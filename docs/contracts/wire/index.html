Wire contracts

Status: accepted, 2026-11-25. Companion to architecture.md §3.

Ownership

  • Rust structs in crates/fluid-core are the source of truth for every wire type. They use #[serde(rename_all = "camelCase")]; TypeScript follows, never the reverse.
  • TypeScript types will be generated by fluid-contracts-gen into packages/contracts/src/generated/. That crate is not in the workspace yet; until it lands, packages/contracts/src/*.ts mirrors the structs by hand.
  • zod is only for untrusted boundaries: MCP input, agent output, URL state, plugin manifests, and fixture tests. Do not re-validate a response Rust just produced; that hides drift instead of catching it. The fixture tests are the drift alarm.
  • A contract change requires, in one PR: a Rust test, a fixture update, regenerated TypeScript, and a web typecheck.

Casing and nullability

Every wire field is camelCase. Enums are lower-camel strings:

Enum Values
EntityKind package, namespace, class, interface, trait, method, field, file, unknown
RelationKind calls, references, inherits, implements, imports, contains, remote, extends
RelationProvenance scip, tree-sitter, live, manual
TagStatus accepted, proposed, rejected
TagAuthor human, agent, rule, import
FileStatus added, modified, deleted, renamed
CheckStatus pass, warn, fail, skip
RiskLevel low, medium, high
IntentSource agent, commit, user

head is null for a working tree. ChangeBrief always emits it. Impact and get_diff serialize it only when it is Some, so parsers must treat a missing head as null.

Stable keys

  • Entity key: a provider-stable key (SCIP, Pharo <package>/<Class>#<selector>, or a file key). Never derive it from row order or a display name alone.
  • Cell id: <layer>:<domain>, e.g. business:codegraph.
  • Tag id: <slug>-<16 hex FNV-1a>, computed from target.key; the file is .fluid/tags/<id>.json. target.key is the only join to the graph.
  • Generation: an opaque string that changes on any index mutation. Cache entries are keyed by (generation, query); never reuse a matrix across generations.

Tag status vs computed orphan

status is durable and stored in .fluid/: accepted, proposed, or rejected.

orphaned is computed at read time: the tag’s target.key does not resolve in the current graph. It is never stored. Rejected tags are ignored by orphan detection. list_tags returns { "tag": ..., "orphaned": true | false } so the two concepts never get conflated in the UI.

Matrix

{
  "generation": "7f3c1a9e-42",
  "lens": "layer-domain",
  "layers": [{ "id": "business", "label": "business", "order": 1 }],
  "domains": ["codegraph"],
  "cells": [
    {
      "id": "business:codegraph",
      "layer": "business",
      "domain": "codegraph",
      "size": 1,
      "symbolKeys": ["src/codegraph/SymbolLinker.ts#SymbolLinker"]
    }
  ],
  "edges": [{ "from": "entry:workspace", "to": "business:codegraph", "weight": 2 }],
  "stats": { "files": 1, "symbols": 1, "edges": 1, "elapsedMs": 3.8 },
  "warnings": []
}

size equals symbolKeys.length. Edges are cell-level and directed from depends on to.

Impact

{
  "base": "main",
  "head": null,
  "changedFiles": ["src/codegraph/SymbolLinker.ts"],
  "changedSymbols": ["src/codegraph/SymbolLinker.ts#SymbolLinker"],
  "changedCells": ["business:codegraph"],
  "impactedCells": [
    { "id": "business:review", "distance": 1 },
    { "id": "entry:workspace", "distance": 1 }
  ],
  "warnings": []
}

Impact propagates along incoming edges: a cell that depends on a changed cell is impacted. distance is the number of edges from the nearest changed cell and is never 0.

Tag values are a string or a string array. provenance.confidence is 0..1 and only meaningful for agent proposals.

Change Brief

{
  "version": 1,
  "id": "cb-5f2a8c1d9e3b7a40",
  "base": "main",
  "head": null,
  "createdAt": "2026-11-25T11:42:00Z",
  "files": [
    { "path": "src/codegraph/SymbolLinker.ts", "status": "modified", "additions": 12, "deletions": 13 }
  ],
  "symbols": { "changed": [{ "key": "src/codegraph/SymbolLinker.ts#SymbolLinker", "name": "SymbolLinker", "kind": "class" }] },
  "cells": { "changed": ["business:codegraph"], "impacted": [{ "id": "business:review", "distance": 1 }] },
  "tags": { "touched": ["symbollinker-4b2c8d1e6f7a9b3c"], "proposed": [], "orphaned": [] },
  "checks": [{ "id": "typecheck", "label": "Typecheck", "status": "pass", "evidence": [] }],
  "risk": { "level": "medium", "factors": [{ "id": "cross-layer", "label": "Cross-layer edge", "weight": 0.6 }] }
}

tags.touched, tags.proposed and tags.orphaned contain tag file ids, not target names. Facts are deterministic; intent and narrative are optional enrichments and never replace evidence.

MCP tools

Every advertised tool is in packages/contracts/src/mcp-tools.ts (mcpTools). A test asserts that mcpToolNameSchema and the registry have exactly the same names.

Tool Input Output
get_matrix lens?, ref? matrix projection: generation, layers, domains, cells, edges, warnings
cell_symbols cells[], limit, offset { total, symbols[] } with key, name, kind, file
get_entity key { entity: { key, kind, name, file?, tags?, note? } }
get_relations key, direction, kind?, depth { relations[] } with from, to, kind, weight, depth
get_impact base?, head? changed files/cells, impacted cells, warnings
get_diff base?, head?, path? { base, head, files[] with hunks, truncated }
list_tags status?, orphaned?, limit, offset { total, tags: [{ tag, orphaned }] }
propose_tag target, tags, note?, evidence?, confidence? { proposal, accepted }

propose_tag is a write. It requires the configured trust mode and is audited like every mutation. get_diff and list_tags have no Rust struct yet; the Rust track must implement outputs that match these schemas (or change both sides together).

Fixtures

fixtures/contracts/{matrix,impact,tags,change-brief}.json describe one coherent workspace: the same cells, symbol keys and tag ids everywhere. They are parsed by packages/contracts/src/fixtures.test.ts today and must also be parsed by cargo test once the Rust track adds the fixture reader. Run:

pnpm --filter @fluid-coding/contracts test

When a fixture fails, first decide which side is wrong. If Rust serializes it, Rust wins and the fixture/TS follow. Never change Rust to satisfy a hand-written TypeScript shape.

Tasks

Task types live in crates/fluid-core/src/tasks/; packages/contracts/src/tasks.ts mirrors them and fixtures/contracts/tasks.json is the drift alarm. See ADR-0011.

Enums: TaskSource = local, github, gitlab; TaskStatus = todo, in_progress, in_review, done (snake_case on the wire; local frontmatter uses todo, in-progress, in-review, done).

Stable keys: local:12, github:owner/repo#12, gitlab:group/project#7. They are opaque and percent-encoded in path segments.

{
  "version": 1,
  "key": "local:12",
  "source": "local",
  "number": 12,
  "title": "Add task tracking to fluid-coding",
  "body": "## Context\nOne board across providers.\n\n## Acceptance criteria\n- [ ] API routes\n\n## Out of scope\nChat editing.",
  "status": "in_progress",
  "parent": "local:4",
  "children": [],
  "labels": ["core", "tasks"],
  "assignees": [],
  "milestone": "M1",
  "branch": "12-add-task-tracking",
  "createdAt": "2026-11-25T10:00:00Z",
  "updatedAt": "2026-11-25T11:30:00Z",
  "links": { "symbols": [], "cells": [], "changes": [], "pullRequests": [] }
}

remoteUrl and remoteKey are optional; links holds symbol keys, cell ids, Change Brief ids and pull request URLs. A brief is derived, not stored:

{
  "key": "local:12",
  "shortId": "#12",
  "title": "Add task tracking to fluid-coding",
  "status": "In Progress",
  "context": "One board across providers.",
  "acceptance": [{ "text": "API routes", "done": false }],
  "outOfScope": "Chat editing.",
  "branch": "12-add-task-tracking",
  "commitFooter": "Refs #12",
  "filesToRead": [],
  "commands": [],
  "rules": []
}

Routes under /api:

Route Notes
GET /tasks statuses, labels are comma-separated; also source, milestone, parent (root for top-level), search, limit (default 200), offset
POST /tasks creates a local task only; source: github/gitlab is rejected
GET /tasks/providers manifests with capability flags; advertisement only, not a live connection
GET, PATCH /tasks/{key} read or patch a normalized task; no forge write
GET /tasks/{key}/brief files, commands, rules are comma-separated context lists
GET /tasks/{key}/local.md { "markdown": "..." } for local tasks only

Local Markdown uses board.py frontmatter (id, title, status, parent, branch, remote, created, updated, labels, assignees, milestone, plus remote_key and fluid link keys) and a body with ## Context, ## Acceptance criteria checkboxes and ## Out of scope. Parsing tolerates unknown keys; serialization emits that shape so the file stays usable by board.py.

GitHub/GitLab are represented only as normalized snapshots, fixtures and provider capabilities. No forge API calls are made in this slice; adapters are a later implementation step.

The same types back three read-only MCP tools: list_tasks (filtered task list), get_task (one normalized task) and task_brief (deterministic handoff with optional files/commands/rules). Write tools stay absent from MCP; agent patches go through the edit routes below under explicit trust.

Edits and checkpoints

packages/contracts/src/edit.ts mirrors fluid_core::plugins::edit. A PatchProposal has an optional blank id (assigned by the server), a taskKey, a summary and at least one FilePatch. A file patch uses camelCase oldStart/oldLines/newLines hunks, or an after string that replaces the whole file. Hunk validation is pure and applies bottom-up; whitespace around expected lines is ignored. A missing file is read as empty so patches can create files. Paths must be relative to FLUID_WORKSPACE and cannot contain ...

Routes under /api:

Route Notes
POST /edits/propose validates and stores a proposal; assigns edit-N when id is blank
GET /edits lists stored proposals
GET /edits/{id} one proposal
POST /edits/{id}/apply `{ “trust”: “edit”
GET /checkpoints summaries: id, label, createdAt, files
POST /checkpoints/{id}/restore { "restored": [paths] }

TrustMode is propose, edit, auto on the wire (snake_case in Rust). Before every write the server creates a checkpoint with the exact prior contents; apply uses a temp sibling plus rename, and restore writes checkpoint contents back. Restoring a checkpoint for a previously missing file leaves an empty file in this first slice. Checkpoints and proposals are in-memory until persistence lands.

Agents and narrative

packages/contracts/src/agents.ts mirrors the agent, narrative and plugin registry contracts. An AgentRequest has taskKey, prompt, trust (default propose), optional files and brief. An AgentResponse has agent, session, patches, messages and optional narrative. CLI output is validated as untrusted JSON before mapping; process failures become typed plugin errors.

Routes under /api:

Route Notes
GET /agents/plugins manifests for fake, opencode, claude-code
POST /agents/{id}/run one agent turn; unknown id is 404, blank taskKey is 400
GET /narrative/plugins manifests for deterministic, cli
POST /narrative/{id} optional enrichment from deterministic facts only

NarrativeRequest carries facts, tone and maxWords; NarrativeResponse carries text, provider, model and deterministic. Narrative never changes facts, checks, impact or trust decisions. The cli adapter reads FLUID_LLM_CMD (default claude -p) and passes argv, never a shell string.

Language providers

packages/contracts/src/language-provider.ts exposes provider manifests and a pure languageQuery helper. Built-in static providers are typescript-static, javascript-static, java-static and pharo-static; their ids, languages and capabilities come from the Rust manifests, not TypeScript.

Routes under /api:

Route Notes
GET /languages/plugins built-in manifests from builtin_language_plugins()
POST /languages/query { path, source?, language?, symbols?, relations? }; language defaults to classify(path)

The response is { providerId, symbols, relations } with the shared code-graph entity/relation schemas. Unknown extensions and unknown languages return 400. Live Pharo via PLexus/MCP is a later adapter with the same LanguagePlugin trait; the static Tonel provider ships in the POC.
