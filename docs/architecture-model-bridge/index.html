Architecture: the badetitou/model bridge

Boundary

fluid stays the shared contract and UI layer: fluid-core owns CodeGraph, the matrix spec, change briefs and impact requests; fluid-server owns the HTTP wire shapes and the web app renders them. It is not a second source of truth for graph algorithms or language knowledge.

badetitou/model is the canonical analysis and language engine:

  • model-core — language-neutral Model, ModelBuilder, stable keys, kinds, relations and sites.
  • model-analysis — deterministic read-only analyses: Cycle, Propagation, metrics, degrees.
  • model-detect — language detection for a source tree and its project roots (aligned separately).
  • model-lang-rust (later) — SCIP-backed Rust frontend, replacing heuristic extraction when ready.

This bridge lives in crates/fluid-index/src/model_bridge.rs, the adapter layer that already turns real files into a CodeGraph. It depends only on fluid-core plus the published 0.8 crates; no other crate or route was changed.

What the bridge does

to_model(&CodeGraph) -> model_core::Model freezes fluid entities into a ModelBuilder:

  • fluid’s stable key is the model key and name is the display name;
  • Package/Namespace → Namespace, Class → Class, Trait → Trait (the dedicated 0.8 archetype), Interface, Method, Field and File keep their names;
  • Unknown → fine kind unknown (archetype Variable, model-core’s own generic fallback), because 0.8 has no Unknown archetype. kind_name() identifies it without guessing a type;
  • parent_key becomes a parent link when that entity exists; file + range become a source; language becomes a LanguageId; external is carried over;
  • relations use Provenance::Derived: Calls → Calls, References/Remote → References, Inherits/Extends → Inherits (model-core’s superclass relation), Implements, Imports unchanged, Contains → Other("contains") (containment is a parent in model-core). Endpoints not present in the graph are skipped — no facts are invented. A site reuses the source entity’s range when known; otherwise the relation is asserted without a site.

analyze, analyze_with_depth and analyze_with_seeds delegate cycles to model_analysis::Cycle and impact to model_analysis::Propagation with Direction::Callers, Calls + References edges and depth 3 by default. Results are sorted by key so two runs on the same graph are byte-for-byte identical. ModelAnalysis carries cycles (components of two or more entities), cyclicEntities, selfCalls / selfCallCount (single-entity components, kept apart because name-resolved call edges produce many false self-calls), propagation (key, distance, direction), degrees (top fan-in + fan-out rows), unused / unusedCount (isolated source entities, capped), entityCount, relationCount and warnings. GET /api/model/analysis serves it with the index generation, computed once per generation. It also serves baseline and a signed delta (ADR-0039): the current counters minus the same counters of a baseline tree. The baseline is the target branch of an open PR/MR for the current branch, otherwise HEAD; fluid-index exports that commit with git archive into a temporary directory, indexes it with the same plugins and runs the same engine. When no baseline can be inspected, delta is null and baseline.note says why. The browser only formats those numbers.

Seeds come from the changed symbols supplied by the caller (Changed::symbols or ImpactRequest::changed_symbols). CodeGraph itself has no change set, so analyze and analyze_with_depth use the documented fallback: entities with no parent. Unknown seed keys are ignored; if no seed resolves, the same parentless fallback applies. A failed upstream analysis is reported in warnings rather than silently replaced with guessed data.

Compatibility

This is additive. Nothing in fluid-server, fluid-core, apps/web or packages/contracts changes: /api/matrix keeps its MatrixSpec shape and /api/impact keeps its Impact, ImpactRequest and cell-distance semantics. Those routes still use the existing, explainable cell-level BFS. A future route can expose ModelAnalysis (for example /api/model-analysis) without altering existing clients; until then this module is a library API covered by colocated unit tests.
