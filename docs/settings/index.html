Settings: General vs Project

Settings are split by scope. The split is deliberate: an LLM choice is a property of the machine, while repos, trust and plugins are properties of a local checkout.

The header pill reports the server’s own answer from GET /api/health: the dataSource it reports, a loading state, or an explicit health error. In local mock mode it says demo fixtures; build mode alone never produces a server connected claim. A failure to read GET /api/settings/project is shown as an alert in the Project tab rather than being hidden behind a loading note.

General settings (machine-level)

The General tab manages the LLM providers available on this machine:

id label default command
opencode opencode opencode run --format json
codex Codex codex exec --json
claude Claude claude -p --output-format json
copilot Copilot copilot -p
ollama Ollama from the first installed model

Defaults are one-shot and, where supported, ask for JSON so the dock can show a real answer or a real error. They can be overridden per provider. Ollama has no hard-coded model: the server reads the names from the local daemon (GET /api/tags, OLLAMA_HOST or http://127.0.0.1:11434), the UI offers those names, and saving remembers ollama run <model>. The first installed model is the proposed default; the last saved choice wins on later runs (ADR-0026). With no installed model the dock reports the missing model instead of guessing. Ollama’s CLI returns plain text rather than the agent JSON object, so the dock shows the answer as a message; patches still require a model that follows the requested JSON contract.

  • Autodetection is a deterministic executable lookup of the first token of the effective command: the inherited PATH, then Homebrew (/opt/homebrew/bin, /opt/homebrew/sbin), /usr/local/bin and the per-user ~/.local/bin and ~/.opencode/bin directories. The extra directories matter for a GUI launch, which does not read shell profiles: the opencode installer puts its binary in ~/.opencode/bin and only adds it to the shell PATH. It does not spawn a process, run a shell or call the network. A path is reported only when it is a file with an executable bit (on Unix); directories and non-executable files are ignored.
  • Overrides replace the default command for one provider. Commands are plain argv tokens: blank values and shell metacharacters (; & | $ \ newlines quotes < >) are rejected.
  • Selection chooses the provider used by the Fluid Agent in the dock; with no selection the settings view still shows the documented claude -p as a display fallback, but the agent refuses to run until a provider is chosen explicitly (ADR-0024).
  • Navigation rail: the left/right position is a machine-level General setting. It is applied to the shell as soon as it changes and persists with the other General values; no reload is needed.
  • Tracing: sessionTracing decides whether local agent runs emit OTLP traces and captureGenAiContent opts in to recording prompts and tool payloads. Both are General toggles, defaulting to prompts and payloads off; they apply immediately to the next agent run (ADR-0027).
  • Storage: <home>/.fluid-coding/general-settings.json, version 1, with selected, commands, theme, railPosition, sessionTracing and captureGenAiContent. <home> is FLUID_CODING_HOME, otherwise HOME, with <FLUID_WORKSPACE>/.fluid-home and ./.fluid-home as last-resort fallbacks (ADR-0022). This keeps machine-level settings out of checkouts and out of the process working directory, which is read-only when the macOS app is launched from Finder. The path is resolved once at startup. A missing or invalid file falls back to defaults; writes are atomic (temp file + rename) and contain no secrets.
  • Endpoints: GET /api/settings/general and PATCH /api/settings/general. Every change applies to the UI and the Agent dock immediately, then persists through one debounced (250 ms), serialized write. There is no Save general settings button; a failed write surfaces inline.

Selecting a provider, moving the rail, changing a command or toggling tracing never changes deterministic facts, never re-indexes a repo and never writes to the repository.

Themes

General settings also choose the interface theme. Six built-in themes are available:

id mode source
fluid-dark dark fluid-coding’s original workbench palette
badetitou-light light fluid’s badetitou design tokens
badetitou-dark dark fluid’s badetitou design tokens
solarized-light light fluid’s Solarized theme
solarized-dark dark fluid’s Solarized theme
high-contrast dark/light fluid’s high-contrast theme, following the OS preference
  • Theme tokens are ported from badetitou/model’s companion design system in fluid; the CSS variables in styles.css are remapped through data-theme on <html>.
  • The choice is stored in general-settings.json as theme and applied as soon as it is selected, without a Save step. No repository file is touched.

Project settings (local checkout)

The Project tab is a read-only view for now of the currently active project declared in .fluid-coding/project.json in the project root. It has no editable fields:

  • identity (id, name, root);
  • repositories (key, relative path, languages);
  • default trust (propose, edit or auto);
  • enabled plugins and task providers;
  • data source (real for an indexed project, demo before setup);
  • warnings produced while loading the workspace.

When no project is configured, the tab says so honestly: it shows the workspace root and data source rather than inventing a project. To create or change the declaration, use the quiet Reconfigure this project link, which opens /setup. Setup is the only place that applies a project proposal to the filesystem. The read endpoint is GET /api/settings/project.

What is not here

Forge accounts and agent sessions/conversations are outside the General/Project split: forge connections are managed from their own surface and agent work happens in the dock and on the Agents tab. Agent teams (.fluid/teams.json) have their own Teams rail view, just above the Settings gear, not a Settings tab. Language providers and performance budgets also belong to their own surfaces. General settings contain only machine-level provider commands and selection, theme, rail position and tracing flags; the Project tab is read-only and holds no machine-level secrets or overrides.
