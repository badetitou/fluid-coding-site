Architecture

Status: accepted, 2026-11-25. Supersedes the TypeScript/Fastify topology in the earlier plan and the read-only POC sequencing in earlier notes (ADR-0012).

1. Shape

fluid-coding is a local-first Structure workbench. The browser is a view; the Rust workspace owns the graph, the index, tags, changes, agent sessions and patch/checkpoint state.

┌───────────────────────────────────────────────────────────────┐
│ Browser (React 19, TypeScript, Monaco loaded lazily)           │
│ Now · Structure · Code · Changes · Tasks · Agents · Settings   │
│ renders JSON, local filtering only, virtualized lists          │
└───────────────┬───────────────────────────────┬───────────────┘
                │ HTTP + SSE                    │ wasm-bindgen
┌───────────────▼───────────────┐   ┌───────────▼───────────────┐
│ fluid-server (axum, native)   │   │ fluid-wasm (browser/edge) │
│ fs · git · process · MCP      │   │ read-only analysis demo   │
│ agents · checkpoints · web    │   │ worker-safe, no I/O       │
└───────────────┬───────────────┘   └───────────┬───────────────┘
                └───────────────┬───────────────┘
                        ┌───────▼────────┐
                        │  fluid-core    │
                        │ pure Rust      │
                        │ graph · matrix │
                        │ impact · tags  │
                        │ tasks · ports  │
                        │ patches        │
                        └────────────────┘

The same core runs native and WASM. It never opens a file, runs a command, reads a clock, or awaits a future. Time, paths, I/O and process calls are passed in by adapters.

The first POC is installed as a macOS .app: fluid-cli embeds apps/web/dist, serves it from a loopback-only axum server and opens the browser. Desktop and hosted modes come later.

Crate Depends on Must not depend on

Dependency direction is one-way: cli/server → index → core. A feature request that would put I/O in core is rejected; add a port and an adapter instead.

3. Wire contracts

Rust is the source of truth.

  1. Domain structs live in fluid-core, with serde(rename_all = "camelCase") except where the wire contract deliberately uses snake_case (trust modes, task status query values).
  2. TypeScript contracts mirror the Rust structs in packages/contracts; shared JSON fixtures are the current drift alarm. Generated types remain the target once the generator lands.
  3. zod schemas validate untrusted boundaries: agent output, LLM output, MCP input, URL state, plugin manifests and server JSON.
  4. A contract change requires: Rust test, fixture update, TypeScript typecheck and web test.
  5. No any in TypeScript; no panics in request paths in Rust.

4. Request path

GET /api/matrix?ref=HEAD
  → axum handler
  → WorkspaceService generation (git oid + index epoch)
  → cached CodeMatrix
  → JSON

Rules:

  • No handler calls git or the filesystem on every request. Index and matrix are cached by generation.
  • Mutations bump the generation and invalidate dependent caches.
  • Long operations return a job id and stream progress over SSE.
  • Every response is typed, size-bounded and trace-instrumented.
  • /api/health is cheap and never blocks on the index.
  • /api/tasks*, /api/edits*, /api/checkpoints*, /api/agents/* and /api/narrative/* use the same typed error mapping and zod-validated payloads.

5. Indexing

files ──► tree-sitter ──► symbols/ranges ─┐
       ──► SCIP index ──► exact relations ──┼──► CodeGraph
       ──► git ─────────► diffs/history ────┘        │
                                                    ├─► matrix (layer × domain)
                                                    ├─► impact (reverse BFS)
                                                    ├─► tags / orphans
                                                    ├─► change briefs
                                                    └─► MCP tools

Model gives fine-grained SCIP-keyed entities. Structure gives the layer × domain quotient, cell symbols and impact. SymbolLinker joins by SCIP key, then by file + name + range, with a confidence badge.

Incremental path: file watcher → debounce → reparse changed files → update graph slice → recompute matrix cells and impact → bump generation → SSE generation event.

Language support is plugin-based: TypeScript/JavaScript and Java static providers plus a Pharo Tonel static provider ship in the POC; live Pharo via PLexus/MCP uses the same LanguagePlugin trait.

6. Tags, changes and edits

Tags are durable annotations in .fluid/tags/*.json, keyed by a provider-stable symbol key. The server loads them at startup, watches the folder, and keeps a derived index in memory. SQLite is a cache, never the source of truth.

A Change Brief is assembled deterministically, then optionally narrated by an LLM. Facts come first: files, symbols, cells, impacted cells, relation changes, touched/orphaned tags, checks, risk factors. The narrative never replaces the evidence.

Chat turns propose patches through PatchProposal/FilePatch/PatchHunk. apply_hunks is pure and runs bottom-up. Before any write, the server creates a Checkpoint with the exact previous file contents. Default trust is propose; edit and auto are explicit and still checkpoint every write. Paths are workspace-relative and traversal is rejected.

7. WASM and online

There are two online paths:

  1. Hosted workspace server (same Rust binary in a container): full features, git, filesystem, MCP.
  2. WASM-only mode (browser/edge): open a fixture or a public repo snapshot, compute matrix, impact and tag queries in a worker. No writes, no process, no filesystem.

The WASM facade exposes coarse calls, not chatty getters:

buildMatrix(graphJson, specJson, generation): string
analyzeImpact(graphJson, specJson, changedJson, base, head): string
findOrphans(tagsJson, knownKeysJson): string

For large graphs, the worker owns the wasm instance and transfers JSON once. The UI never blocks the main thread on graph work.

8. Web shell

  • React 19 + Vite, no antd, no component framework in the coding shell.
  • CSS modules or a single tokenized stylesheet; no hardcoded colors in components.
  • Route-level code splitting; initial bundle budget 150 KB gzip.
  • Graph rendering: custom canvas for the map, SVG for small diagrams; only visible cells draw.
  • Tables are virtualized above 100 rows.
  • State: URL for selection, a small store for server cache; no graph semantics in the client.
  • Monaco is the code surface, loaded lazily with LSP-style navigation. “Open in VS Code” is the escape hatch, not the editor.
  • The agent dock is persistent across routes: task brief → chat turn → patch review → apply → checkpoint. Its width is a browser-local shell preference, resized from the left divider; it stays out of the shared settings contract and out of the repository.
  • Session analysis is a dedicated lazy route /analysis?ids=...&expand=... under Shell, opened from Agents for one session or a multi-selection; it adds no primary nav item. @xyflow/react v13 and its stylesheet load only with that route. React Flow is the session-graph surface; the structure map keeps its custom canvas. Rust computes node positions and batching, React only renders them (ADR-0028).

9. Plugin seams

fluid-core/src/plugins owns contracts; upper layers own adapters and I/O.

Kind Core contract POC adapters
Agent AgentPort, AgentRequest, AgentResponse MCP tools, fake, opencode, Claude Code
Language LanguagePlugin, LanguageProvider TypeScript, JavaScript, Java, Pharo Tonel; live Pharo later
Narrative NarrativePort, NarrativeRequest deterministic offline, optional CLI/LLM adapter
Editor patch/checkpoint types and apply_hunks Monaco surface, “Open in VS Code” action

PluginManifest and PluginRegistry expose capabilities, runtime and permissions to the UI and to agents. Adding a capability means implementing a port, registering a manifest and adding a test; routes and components stay generic. See ADR-0013 and the plugin authoring guide.

A plugin can be web-only (TypeScript/CSS in a UI slot), WASM (portable analyzer or check in a worker), or native Rust (fast parser, graph/index hot path, or external process adapter). kind chooses the contract; runtime chooses where it runs. Frontend plugins consume ports through the host API and never write data directly. Native speed does not bypass AgentPort, validation, trust mode or checkpoints.

To add a plugin: write the manifest, implement the chosen tier, add an example and a contract test, document permissions and slots, then register it in a plugin collection. Built-ins follow the same path.

10. Agents

AgentPort is the one seam for MCP, opencode, Claude Code, the in-app agent and test doubles. The POC contract is deliberately small and object-safe:

pub trait AgentPort: Send + Sync {
    fn manifest(&self) -> PluginManifest;
    fn run<'a>(
        &'a self,
        request: &'a AgentRequest,
    ) -> Pin<Box<dyn Future<Output = Result<AgentResponse, PluginError>> + Send + 'a>>;
}

AgentResponse carries messages, patch proposals and optional narrative. Streaming session lifecycle (start/send/cancel) is an additive extension of the same port. MCP remains the external tool contract: get_matrix, cell_symbols, get_entity, get_relations, get_impact, get_diff, list_tags, propose_tag, plus task reads. Every write path requires trust mode and is audited.

Span ingestion is an additive part of the same AgentPort adapter boundary: CLI adapters inject a loopback OTLP endpoint into the spawned provider, the server accepts OTLP/HTTP JSON at POST /_telemetry/v1/traces, and fluid-core holds the pure normalized trace and graph types. Correlation uses traceparent, then conversation/session id plus time. Content capture is opt-in and off by default; no native opencode or Claude Code database is read in v1 (ADR-0027).

12. Projects and repositories

A project is a local, multi-repo workspace, not necessarily a monorepo. .fluid-coding/project.json lists member repositories with a stable repoKey, relative path and optional remote. A local index in ~/.fluid-coding/projects.json lets the shell switch projects. See ADR-0014.

The server activates one project at a time but models many: project and repo scopes are additive to the current flat API, entity keys are namespaced as <repoKey>::<path>#<symbol>, and patches/checkpoints record their repo. Path checks are relative to the member repo. Graph, matrix and cache entries are keyed by (projectId, repoKey, commit); cross-repo edges come from explicit dependency data.

The UI has a project switcher, one structure-map lane per repo, repo-scoped Miller columns, repo labels in editor tabs and repo-aware task briefs for agents. A single-repo project is the degenerate case and keeps the current behaviour.

13. POC boundaries

Included: chat patch proposals and checkpoints, opencode/Claude Code adapters, Monaco/LSP, TS/JS + Java + Pharo providers, and a required narrative port with optional model enrichment.

Not in the first POC: hosted multi-user collaboration, CRDT editing, arbitrary plugin sandboxing beyond typed manifests, live forge write-back, and a second private tool loop next to MCP.
