Reviewing GitHub PRs and GitLab MRs

fluid-coding reviews existing pull requests (GitHub) and merge requests (GitLab) from connected accounts. Reviews are read-only: the app fetches review facts and maps them to a Change Brief, then runs the usual impact, risk and narrative pipeline. It never posts comments or approves anything.

See ADR-0016 for the contract and security model.

Set up an account

  1. Create a personal access token with read access to code and pull/merge requests:
    • GitHub: repo (or the equivalent fine-grained read permission).
    • GitLab: api / read_api plus read access to the project.
  2. In Settings → Forge accounts, choose GitHub or GitLab, enter a label (for example Work GitHub), your username and the token.
  3. For self-hosted GitLab, set the base URL to the instance root, e.g. https://gitlab.example.com. Leave it empty for gitlab.com.
  4. For GitHub Enterprise, set the instance host, e.g. https://ghe.example.com. Do not set https://github.com: the public service uses the built-in default.
  5. Apply. The account is stored as a public record plus a server-side secret; the token is never shown again and never sent to the browser. Removing the account also deletes its stored secret.

Only HTTPS base URLs are accepted, with one exception: http://localhost and http://127.0.0.1 are allowed for local test instances (any port).

Review a PR or MR

  1. Open the review list and pick an account. Optionally filter by state: open, merged, closed.
  2. Select a review. Its id is canonical: github:owner/repo#8 or gitlab:group/proj!12.
  3. The detail view shows the title, author, source/target branches, files with additions and deletions, commits and CI checks.
  4. “Map to Change Brief” turns the review into the same fact shape used for local changes. Files keep their paths and add/delete counts, and check URLs become evidence for the check results. The review body and commit messages are context, not evidence.

The token stays on the server: the UI only ever receives ForgeAccount records (no token field), and the contract schemas reject any account response that contains one.

Limits

  • PATs only. Device-code OAuth (oauth_device) is declared in the contract but not implemented.
  • Read-only. forge:write is a declared future capability for comments and approvals; nothing can post to a forge yet.
  • GitHub and GitLab only; other forges need a new manifest and adapter.
  • Reviews are mapped to Change Brief facts, not to a separate review model. Forge APIs do not give symbol keys, so symbols, cells and tags in the mapped brief are empty; no symbols are guessed.
  • File patches are carried on ForgeReviewDetail but are not used as symbol evidence.
  • No polling or webhook ingestion in this release: refresh the list to see new reviews.
  • Empty labels/usernames and PATs shorter than 8 characters are rejected before an account is saved.

Server adapter

The server implements fluid_core::plugins::forge::ForgePort in crates/fluid-server/src/forge. POST /api/forge accepts the tagged ForgeRequest shapes from ADR-0016 and returns the tagged ForgeResponse shapes; request fields and input are validated again on the server. Invalid input, invalid ids and unreachable upstream APIs produce 4xx responses with fixed messages. No error or response body ever contains a token.

Accounts and tokens live under the forge folder of FLUID_CODING_HOME, or <workspace>/.fluid-home/forge when that variable is unset — never inside a project repository or .fluid/. Metadata is an atomically replaced accounts.json; each token is a separate file created with mode 0600 on Unix (and a 0700 directory). Removing an account deletes its token file. The read path only ever returns ForgeAccount records without a token field, and a Debug impl redacts tokens. oauth_device is rejected at the HTTP boundary and in the service; only PATs are stored.

GitHub uses api.github.com, or <baseUrl>/api/v3 for a GitHub Enterprise instance; GitLab uses gitlab.com/api/v4, or <baseUrl>/api/v4 for self-hosted instances. An explicit /api/v3 or /api/v4 in baseUrl is used verbatim. Reviews are discovered from the account’s repositories or projects, then read from PR/MR list and detail endpoints. Canonical ids are parsed back into the API project and number for detail requests. Checks come from GitHub check runs (falling back to commit statuses) and GitLab MR statuses; when neither is available the adapter reports one unknown check rather than inventing a result. GitLab diffs contribute added/deleted line counts.

All adapter and route tests are offline and deterministic: a std-only TcpListener mock serves canned GitHub/GitLab JSON fixtures, and account tests use a temporary home. The mock also records request paths and Authorization headers to assert that the token appears only as Bearer <token> and never in a URL.

Remaining adapter limits

  • Repository/project discovery is capped at the first API page (100 entries) per account.
  • GitLab diffs provide line counts, not GitHub-style per-file additions from the API payload.
  • No polling, webhook ingestion or write endpoints. forge:write remains declared-only.
  • Check APIs are optional: an unavailable check API is reported as unknown, not as a pass.
