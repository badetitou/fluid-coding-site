Adding a plugin

fluid-coding is plugin-first. Every extension follows the same path: a versioned manifest, an implementation for one runtime tier, an example, a contract test, documentation and registration in a plugin collection. Do not import a plugin implementation directly from a page or route.

See ADR-0008 for kinds and ADR-0013 for runtime tiers.

1. Choose the seam and the tier

You want to… Kind Runtime
add a panel, badge, renderer or editor decoration editor web
add a portable analyzer, check or formatter language wasm
add a fast parser, indexer or graph provider language native
add an agent or narrative provider agent / narrative native (process adapter allowed)

Rust is optional for a web plugin. Rust is the default for hot paths. WASM is the default for third-party compute. The native tier uses runtime: "native" for a linked crate and runtime: "process" for an external executable.

2. Write the manifest

The additive runtime fields are specified in ADR-0013; first-POC built-ins predate them and default to native.

{
  "id": "acme-task-badges",
  "label": "ACME task badges",
  "kind": "editor",
  "runtime": "web",
  "host": "web",
  "version": "0.1.0",
  "contractVersion": 1,
  "entry": "./dist/index.js",
  "slots": ["task.card.badge"],
  "capabilities": ["render"],
  "permissions": []
}

Permissions are explicit: workspace:read, workspace:write, tasks:read, network:out, process:spawn. A write plugin must return patch proposals; the host applies them under the current trust mode and always creates a checkpoint.

3. Implement the tier

web

Export mount(slot, host) from the entry module. The host gives typed read APIs and proposePatch. A web plugin never calls bffClient, urql or a write store directly, and never hard-codes colours: it uses the host theme. Keep one component per file and ship CSS, not inline style piles.

wasm

Implement the core port in Rust, compile to wasm32-unknown-unknown and exchange validated JSON with the host. No filesystem, clock or network access inside the module. The same fluid-core crate already has a WASM facade to copy from.

native

Add a crate to the workspace, implement the same port and register it in the server composition root. Process adapters (opencode, Claude Code, LLM CLI) receive argv, never a shell string, and their output is validated before it becomes a PatchProposal or NarrativeResponse.

4. Prove it

Every plugin ships with:

  • an example fixture showing the manifest and expected output;
  • a contract test against the zod/serde schema and a drift fixture;
  • a failure test: a malformed plugin is rejected without taking down the host;
  • a permission test for any requested side effect;
  • a short README.md naming the port, slots, permissions and configuration.

5. Register it

Add the plugin to a collection manifest. Built-ins and third-party plugins use the same registration path. The registry shows id, kind, runtime, capabilities and permissions; the UI renders only slots it is allowed to render.

Checklist

  • Manifest is versioned and validated.
  • Runtime tier is the smallest that works.
  • Contract test and drift fixture pass.
  • No direct network, filesystem or write-store access from web.
  • Writes go through patch proposals, trust mode and checkpoints.
  • Docs, example and registration are in the same commit.
