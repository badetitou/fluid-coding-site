Working with a real project

fluid-index is the filesystem/git adapter that turns a configured project into the same graph, matrix, changes, tags and tasks the UI already renders. AppState uses it whenever a project is configured; with no configured project it still loads crates/fluid-server/fixtures/demo.json so first run, tests and smoke checks have a workspace.

Configure a project

Use Settings → Setup on first run (see setup.md), or write the definition yourself at <project-root>/.fluid-coding/project.json:

{
  "version": 1,
  "id": "atlas",
  "name": "Atlas",
  "repos": [
    { "key": "web", "path": "apps/web", "languages": ["typescript"] },
    { "key": "core", "path": "crates/core", "languages": ["java"] }
  ],
  "activeRepo": "web",
  "settings": {
    "defaultTrust": "propose",
    "plugins": ["typescript-native", "java-native"],
    "taskProviders": ["local"]
  }
}

Paths are relative to the workspace root and must stay inside their repository. repos[].languages is a whitelist (typescript, javascript, java, pharo; empty means all). settings.plugins can name a provider id or a language, with an optional -native/-static suffix. An empty taskProviders list or a list containing local loads .claude/issues/*.md.

Run and see real data

pnpm dev            # web UI; VITE_API_MODE=server proxies /api to Rust
cargo run -p fluid-server

Once AppState loads a real project, the map, Changes, Tags and Tasks pages are built from files on disk: entities from TS/JS/Java/Pharo providers, cell assignments from real directories, changed files from git status --porcelain, tags from .fluid/tags/*.json and tasks from .claude/issues/*.md. warnings in the response explains anything skipped.

Connect GitHub or GitLab issues

Add github or gitlab to settings.taskProviders. The app embeds the public client ids of its GitHub and GitLab OAuth applications, so no environment variable is needed: start the server normally and use the sign-in buttons.

Environment variables are only overrides, for a private OAuth application or a self-managed GitLab instance (17.9+):

FLUID_GITHUB_CLIENT_ID=... cargo run -p fluid-server
FLUID_GITLAB_CLIENT_ID=... FLUID_GITLAB_URL=https://gitlab.example.com cargo run -p fluid-server

On the Tasks page, select Connect GitHub or Connect GitLab, open the verification URL and approve the displayed code. The server stores the resulting token outside the repository and loads up to 100 open issues from the active repo’s origin. Forge issues are read-only in the board; they can still generate a brief and start a local branch.

How the switch works

ProjectRegistry::is_configured() distinguishes a real manifest/index from the synthetic demo project. When it is true, AppState calls fluid_index::load(registry.active()) and converts the result through DemoFields; otherwise it converts the demo fixture the same way. Both paths then feed the existing build_matrix, analyze_impact, TagIndex::from_tags and TaskStore::from_tasks calls unchanged.

GET /api/health exposes dataSource (real or demo), generation (real:<project.id> for a configured project), projectId and the indexer warnings. The expandable status panel shows that source, while the status bar shows the warning count, so a mock run is never mistaken for work on real code.

Use a real agent and a trust/checkpoint flow

Agents connect through AgentPort (fake, opencode, claude-code) and the same MCP tools; there is no private tool loop. Open a task brief, ask the agent for a change, review the proposed hunks, then apply. Default trust is propose: applying is explicit and every write first checkpoints the exact previous file contents, so a restore can undo it. edit and auto are opt-in and still checkpoint. Workspace-escaping paths are rejected.

Current limitations

  • This slice reads the working tree once at startup. There is no watcher/SSE generation refresh yet.
  • Providers are conservative static text scanners, not tree-sitter or SCIP; relations are file-local unless a later provider records typed cross-repo evidence.
  • Layers are directory buckets (src, apps, crates, packages, tests, docs, root) and domains are repo keys. Nothing is inferred by an LLM.
  • Git is optional: if the binary is missing or git status fails, changes are empty with a warning.
  • At most 2000 files and 512 KiB per file are read; symlinks, hidden directories, node_modules, target, dist, build and .fluid-coding are skipped with warnings where actionable.
  • Local POST/PATCH still update the in-memory store until local Markdown write-back lands; creation can now write a real issue on a connected forge (ADR-0023). Tags are loaded, not watched.
  • Non-UTF-8 files, malformed tags/issues and duplicate task keys are reported in warnings and skipped; they never become invented entities.
