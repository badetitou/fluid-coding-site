Home — task composer bar

Status: revision 3 (with the set extension, #99), after the first adversarial review (REJECT, 15 findings — addressed below) and the shared chat field change. Extends home-now.md. Decision records: ADR-0035, ADR-0038.

Purpose

Home becomes the fastest place to create a task for the active project. A full-width bar, shaped like the agent dock’s composer, takes one sentence. The Fluid Agent asks follow-ups if needed and proposes a draft issue with sub-tasks; the user confirms with one click. The bar never writes a task on its own.

It is not a second agent: it reuses POST /api/tasks/intake (ADR-0035) and POST /api/tasks.

Placement

  • Directly under the Home header, above the Now grid, full width of .now-page (max 1320 px).
  • Rendered in every Home branch (loading, error, loaded). The composer hook is called before NowPage’s early return, so typed text survives the first /api/now response.
  • Mock mode (api.mode === 'mock'): the textarea is disabled with the placeholder “Needs the server: run with VITE_API_MODE=server” and the status line says “Needs the server”.

Look

  • The same chat field as the dock (ChatField): › prompt line, two-row textarea, a context chip, a gear popover and chips for trust mode, provider and model, in the same order. No chat shell: no header, tabs, history or New conversation button on Home.
  • Provider and model chips write the same machine-level General settings as the dock and Settings → General. Mode is fixed to propose and disabled: the intake endpoint does not accept a trust mode. The context chip is disabled too: the endpoint sends no files. Both keep a title explaining why.
  • The gear popover shows the active command, an intake note and the link to Settings; the dock’s copy adds its issue input.
  • Status chip: Creates in <project> · ⌘ Enter; the send button title repeats the shortcut.
  • Placeholder: “Describe a task for this project…”.
  • Phone width (375 px): full width with the page gutter; the draft card stacks its buttons.

State machine (pure reducer, pages/now/taskComposer.ts)

Phases: idle → asking → proposed → creating → idle.

Event From Result
input any input updated
send idle/proposed, text non-empty, server online phase asking; user turn appended; request += 1
send asking/creating/mock ignored (single-flight)
intake-ok (same request) asking assistant turn appended; draft = reply draft (null clears it); phase proposed or idle
intake-ok (older request) any ignored (stale after Discard)
intake-fail (same request) asking the message is restored into the input only if nothing new was typed; its user turn dropped; error shown; phase proposed if a draft existed, else idle
create proposed with a draft phase creating; both draft buttons disabled
create-ok creating transcript and draft cleared; notice “Created local:14 in the local board.” with Open the board
create-fail, nothing created creating phase back to proposed; draft kept; error shown (retry or discard)
create-fail, parent created, sub-task failed creating transcript and draft cleared; error “Created local:14, but a sub-task failed: …”; the Board is refreshed so the parent is visible
discard any except creating transcript and draft cleared; request += 1 (in-flight reply becomes stale); typed input kept

Single-flight is enforced twice: the reducer refuses a send that is not allowed, and the hook reads a ref updated synchronously, so two sends in the same tick cannot both reach the API.

Partial creation: the Board’s sub-task loop already leaves a parent behind when a sub-task fails. The design does not retry only the missing sub-tasks (more states for a rare failure); the composer reports the parent and drops the draft, so a retry cannot duplicate the parent. The user creates the missing sub-tasks on the Board. This is the trade-off to confirm.

Sets of linked issues (#99)

One idea often needs several issues. The agent can propose a set instead of one draft:

  • Each item has a ref (short id unique in the set), a title, a body, an optional parent (the ref of another item in the set) and related refs (issues linked without a parent). Children attach to a parent that is also in the set; a set of linked issues has no parent.
  • Each reply carries the complete proposal of the round, for a draft or for a set. The request sends the set the user is reviewing (currentSet), so the agent edits, adds or removes items and returns the whole result. A reply without a set withdraws it, as it does for a draft. A reply never fills both.
  • The card lists every item of the set before anything is created. Children are indented under their parent; the summary gives the counts.
  • Create issues creates the set on the local board only: parents first, each child attached to its new parent key, related titles listed in the body. Forge creation of a set is a separate change.
  • A partly created set is dropped and the failing issue is named, as for a draft with a failed sub-task, so a retry cannot duplicate issues. The Board takes one issue: it reports a set and asks for Home.

Contract: taskIntakeSetItemSchema, set on the reply and currentSet on the request. Rust: task_intake_set.rs validates refs, links, parent cycles and the 20-item limit.

Interaction

  • Send: the send button or ⌘/Ctrl + Enter (same as the dock). A plain Enter inserts a newline.
  • Reply: the last 6 turns show above the bar in the aria-live="polite" log; changing provider or model mid-conversation does not change the state machine.
  • Draft card (section “Proposed task”): title, first 3 non-empty body lines, first 5 sub-tasks then “+N more”, the line “Target: resolved on create (connected forge, else local board)” (the intake reply does not carry the resolved target, so the card says the rule, not a value), and two buttons: Discard and Create task.
  • Focus: when a draft arrives, focus moves to the draft card heading (tabIndex=-1); after Create or Discard the card unmounts and focus returns to the textarea.
  • Asking timeout: none in v1. The intake runs the agent CLI, so it can be slow; while asking the bar shows “•••” and the user can click Discard, which ignores the late reply. Listed as an open point.

Data and contracts

  • No new endpoint, contract or Rust change.
  • Intake: api.intakeTask(messages). Server errors come through as the message: a missing provider gives the server’s “the Fluid Agent is not available” text, which tells the user to pick a provider in Settings. A non-conforming reply is a typed 400 from the server.
  • Create: createTaskWithSubtasks(api, draft, subtasks) in lib/taskCreation.ts, extracted from useTasksBoard.create. The Board keeps its behaviour: refresh, select the new key, notice, close the form. One change: on SubtaskCreationError the Board also refreshes and selects the parent, so the parent is no longer invisible. The composer calls onCreated (refetch Home); the Board refetches on mount.
  • Source: auto, the Board’s default.

Errors

  • Intake failure: one line above the bar, the message is restored into the input, nothing is lost.
  • Create failure: one line under the draft card, as in the table above.
  • An empty reply or missing title is a server error, never a silent draft.

Accessibility

  • The transcript ol is always mounted (empty state hidden with CSS), so the live region exists before the first message.

  • Enter during IME composition never sends.

  • Draft buttons are enabled only in proposed.

  • Textarea aria-label="Describe a task for this project"; send button aria-label “Send” or “Sending”.

  • Draft card labelled “Proposed task”; errors role="alert"; the created notice role="status".

Out of scope (v1)

  • Inline editing of the draft; use the Board form.
  • Choosing a target on Home (auto only).
  • Retrying only the failed sub-tasks.
  • Any conversation selection on Home: no tabs, no history, no New conversation; the dock owns durable sessions (ADR-0038).
  • Changing trust mode or attaching files from Home: the intake endpoint fixes both, so those chips are visible but disabled.
  • Changes tab with patches: the dock owns patch review.
  • Starting work from the composer.
  • Asking timeout (Discard is the escape).

Open points

  • Send key: ⌘/Ctrl + Enter, deliberately different from the dock’s Enter. The shared ChatField owns the look; each surface keeps its own key handler and status hint.
  • Partial creation: drop the draft and report, versus retrying the missing sub-tasks. Chosen: report.
  • Asking timeout: none in v1 (Discard only).
