Home (“Now”) — page spec

Status: draft for validation (W8). Mockup: home-now-mockup.html — open it in a browser, resize to 375 px, toggle the OS light/dark setting.

Purpose

Home answers four questions in this order: what is an agent doing right now, what am I working on, what comes next, what waits for my review. The current page (apps/web/src/pages/NowPage.tsx) is a diff-review page (“Review the current change.”) and answers none of them. Diff review stays on /changes; Home links to it.

Data contract

One request: GET /api/now, one aggregate computed in Rust (AGENTS.md rules 1 and 3). The client never joins sessions, tasks and patches itself. Each section below names the field of the aggregate and the server source that fills it, read once per request.

Field Source (server) Available now?
currentAgent ChatSessionStore (crates/fluid-server/src/chat_sessions.rs): most recent session by updatedAt (one pass over the session files). Status is waiting or done only session yes; running/failed need a run registry and a recorded turn error, which do not exist
currentTask currentAgent.taskKey → task store (project_tasks.rs), accepted only when in_progress or in_review, else the lowest-numbered in_progress task yes
currentTask.worktree fluid_index::existing_task_worktree (read-only, ADR-0029 path); branch = task.branch, else the derived branch_name when the worktree exists yes
currentTask.changedFiles git status --porcelain run in the worktree (fluid-index) deferred, not served
currentTask.lastCheckpoint checkpoint store; checkpoints carry no repo field, only checkpoint_roots maps them to a worktree deferred, not served
nextTask task store: first todo, sorted by milestone (lexical string order, tasks without a milestone last), then number, then key. Task has no priority field, so priority is not in the order yes, without priority
toReview.patches patch store minus AppState.applied_patches (written by apply_patch after all writes succeed, cleared when the matching before <id> checkpoint is restored). Serves id, taskKey, summary, file count; no age or +/- counts (proposals have no timestamp) yes
toReview.checks checks for the current worktree deferred, not served
reviewQueue tags with status = proposed, tasks in_review (counts + first 5). Orphaned tags are deferred (need a graph key set per request) yes
modelHealth index / task-parse warnings are served as warnings (startup snapshot, not refreshed on project switch). Cycles and impacted cells are deferred to W5 warnings only

Each field is independently nullable. A source that fails to read adds one entry to the top-level errors: [{ field, message }] (field is an enum of the aggregate’s fields; today only currentAgent, the only source that does I/O that can fail), so one failing source degrades one card, never the page. The other sources are in memory and cannot fail.

Section order and cards

Desktop (≥ 1180 px content): two columns. Left = Now (1, 2, 4), right = Next (3, 5, 6). Narrow (< 1180 px content, or 375 px phone): one column in the numeric order 1 → 6.

1. Current agent

  • Fields: provider (agent, e.g. claude via Fluid Agent), session title, linked task key, elapsed time since the run started (or “last activity 4 min ago” when idle), status pill running | waiting | done | failed, turn count, trust mode.
  • Actions: Open conversation (opens the agent dock on that session), Stop (running only).
  • “waiting” means the run ended with proposals awaiting review; the pill links to section 4.
  • Empty: “No agent run yet. Start a task or open the agent dock.” with Open dock.

2. Current task

  • Fields: key (local:1), title, status pill, milestone, branch (1-record-demo-videos-in-demo), worktree path (shortened, copyable), changed files in the worktree with +/− counts (max 6, then “+N more”), last checkpoint (label + age).
  • Actions: Open worktree diff (/changes?worktree=…), Reveal in Finder, Mark in review (after W2).
  • Empty: “No task in progress.” + the next-task card’s Start work button is promoted.

3. Next task

  • Fields: key, title, milestone, labels, one-line body excerpt, “N more todo”.
  • Action: Start work → POST /api/tasks/{key}/start (ADR-0029). Button disabled with a tooltip when the task is remote and read-only.
  • Empty: “Nothing in todo.” + New task.

4. To review

  • Patches proposed by agents and not yet applied, grouped by task: summary, files, +/−, age, Review (opens /changes on that patch), Apply (secondary).
  • Checks for the current worktree: compact list, failing first.
  • Empty: “Nothing waiting for review.” (positive tone, no illustration).

5. Review queue

  • Three counted rows, each expandable to at most 5 items: proposed tags (target + confidence bar), tasks in_review, orphaned tags. Link “Review →” to /tags and /tasks.
  • Empty: the section collapses to a single line “Queue empty”.

6. Model health (collapsed by default)

  • Collapsed summary line: 0 cycles · 2 impacted cells · 1 warning, warning tone if any warning.
  • Expanded: cycle list, impacted cells, indexing / task-parse warnings (e.g. unknown task status 'parked' in .claude/issues/1-demo-videos.md).
  • Open/closed state is a per-viewer preference (localStorage), not repository state.

Header

  • Eyebrow: project name · branch of main checkout. Title is the task-centred sentence (“Recording demo videos” when a task is current, “Pick the next task” otherwise). No hero metrics strip: the old four metrics move to /changes.

States

  • Loading: first load shows skeleton cards with the final heights (no layout shift). Refetch keeps the old data visible with a small spinner in the header; budget p95 < 150 ms server side.
  • Error (whole request): one banner at the top “Could not load /api/now — retry”, cards hidden.
  • Error (one field): the card shows its title and a one-line error with Retry; other cards render.
  • Live updates: the page refetches after each agent turn the dock receives, on window focus, and after Start work / Apply. No polling faster than 10 s.

Deferred

  • Until W2 (task persistence + status vocabulary): nextTask ordering by priority, Mark in review, a parked/blocked status. currentTask, nextTask and the in_review queue are served now: they only use todo, in_progress and in_review, which survive ADR-0032.
  • Until W5 (model bridge served): cycles and impacted cells in Model health. Until then the card shows warnings only and says “cycle analysis not available yet”.
  • Not served yet: currentTask.changedFiles, currentTask.lastCheckpoint, toReview.checks, modelHealth cycles / impacted cells, orphaned tags.
  • Worktree-scoped checks: shown when the checks runner accepts a root; until then the card says “checks: main checkout”.

Layout fix: Tasks board squeezed by the agent dock at 1440 px

Measured: 1440 − rail 36 − dock 410 − padding 60 ≈ 934 px of content, while .tasks-layout needs 4 × 220 + 3 × 10 (board) + 16 + 300 (detail) ≈ 1226 px. The max-width: 1180px media query only reads the viewport, so it never fires with the dock open, and the board’s “In Review” column is cut.

Recommendation: container queries on the content area. Set .shell-content { container: content / inline-size; } and move the layout breakpoints of pages that share space with the dock from @media (max-width: 1180px) to @container content (max-width: 1240px). On Tasks the detail panel then drops below the board (or the board gets the full row) whenever the dock makes the content narrow, at any window size. Home uses the same container breakpoint for its two-column → one-column switch.

Rejected alternative: collapsing the dock by default on Tasks. It hides the conversation that Start work just opened (ADR-0029 decision 3) and only fixes one page.

Component plan (for the implementation, ≤ 150 lines each)

NowPage (layout only) · CurrentAgentCard · CurrentTaskCard · NextTaskCard · ReviewCard · ReviewQueueCard · ModelHealthCard. Formatting (elapsed time, file list truncation, empty-state selection) lives in pages/now/model.ts with Vitest tests. The aggregate type comes from the Rust struct (generated, AGENTS.md rule 6) with a zod schema at the fetch boundary and a shared fixture.

Open points

  • Session status: ChatSession has no status field. running needs the in-flight run registry, failed needs the last turn’s error recorded. Proposed derivation, to confirm: in-flight → running; the session’s latest turn proposed a patch still pending → waiting (implemented, session-specific); last turn error → failed; otherwise done.
  • Branch format: the code produces {number}-{slug} (fluid_core::branch_name), not task/{number}-….
