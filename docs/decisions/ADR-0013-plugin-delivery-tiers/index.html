ADR-0013 — Plugin delivery tiers: web, WASM and native Rust

  • Status: accepted
  • Date: 2026-11-25

Context

fluid-coding is a plugin-first platform. A contributor who only wants to add a panel, a tag renderer or a task-card decoration should not have to write Rust. At the same time, code intelligence, graph building and impact analysis are hot paths where a native Rust implementation is much faster than JavaScript or an interpreted plugin. A single “plugin” shape that forces one runtime would make both cases painful.

ADR-0008 fixed typed plugin kinds. This ADR fixes where a plugin executes and what it is allowed to touch, independently of its kind.

Decision

Every plugin has one versioned manifest. kind says what contract it implements; runtime says where it executes. The manifest gains additive fields: runtime, host, entry, permissions, slots and contractVersion. Older manifests default to the current native built-in runtime so the wire stays compatible.

Three delivery tiers are supported:

Runtime Language Host Good for Trust
web TypeScript + CSS browser panels, widgets, renderers, task/tag decorations low: no direct I/O or writes
wasm Rust or another WASM language worker or server portable analyzers, checks, formatters, third-party compute medium: validated JSON, no ambient I/O
native Rust crate or process fluid-server parsers, graph/index hot paths, external agent/LLM CLIs high: explicit opt-in and permissions

There are three delivery tiers but four runtime values: web, wasm, native for a linked Rust crate, and process for an external executable. process is the native tier’s sandbox-friendly shape.

All tiers speak the same ports: AgentPort, NarrativePort, LanguagePlugin, and the patch/checkpoint contracts. A web plugin consumes ports through the host API; it never calls bffClient, urql or a write store directly. A wasm or native plugin implements a data-producing port and returns validated JSON. A native process adapter (opencode, Claude Code, LLM CLI) still goes through AgentPort or NarrativePort; speed does not bypass the contract.

The activation lifecycle is: discover → validate manifest and contract version → check permissions → activate → bind ports and UI slots → run contract test → usable. A broken plugin fails in isolation and is reported in the UI; it never takes down the workbench.

permissions is explicit: workspace:read, workspace:write, tasks:read, network:out, process:spawn. Any plugin asking for workspace:write must produce patch proposals and go through the existing trust mode and checkpoint flow. network:out and process:spawn require user consent.

Adding a plugin always means the same set of artifacts:

  1. a manifest with id, kind, runtime, version, capabilities, permissions and contract version;
  2. an implementation for the chosen tier (.tsx + CSS for web, WASM module for wasm, Rust crate/process for native);
  3. an example and a contract test beside it;
  4. a short README.md explaining the port, permissions and slots;
  5. registration in a plugin collection, never an ad-hoc import in a page or route.

Built-in plugins use the same path. Today’s fake/opencode/Claude Code agents, static language providers and deterministic narrative are native built-ins; Monaco is the built-in web editor surface; the pure Rust core is also compiled to WASM for portable reuse.

Consequences

  • Frontend-only contributors can extend the UI without a Rust toolchain.
  • Hot paths can stay native Rust without changing the UI or wire contracts.
  • Third-party compute defaults to WASM; native and process plugins are explicit trust decisions.
  • The registry must expose runtime and permissions, not just capabilities.
  • Manifest fields are additive; zod and serde schemas plus a fixture are the drift alarm.
  • New plugin kinds still require an ADR or contract proposal, as ADR-0008 says.
