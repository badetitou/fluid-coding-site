ADR-0024 — The Fluid Agent follows the selected LLM provider

  • Status: accepted
  • Date: 2026-11-26

Context

The dock was labelled “Fluid Agent” but defaulted to the fake plugin, while the machine-level General settings already stored a selected LLM provider and command. That selection was display-only: effectiveCommand was rendered in Settings but never used to run anything. Developers could pick a provider and still get deterministic demo patches in the chat.

Decision

Add a virtual fluid AgentPort adapter. On every run it reads ~/.fluid-coding/general-settings.json through the existing server settings store, resolves selected plus its command override, and delegates to a CLI adapter that spawns that command with the prompt as argv. The CLI runs with the active project root as its working directory. JSON output is mapped to the core AgentResponse; plain text becomes a message. No selection is an explicit error, not a silent fallback. The dock always calls fluid and shows the resolved provider; direct opencode/claude-code ids stay available for compatibility. fake remains a test/demo double and is never the default in a connected app.

Consequences

  • One source of truth for the in-app agent: Settings → General. Changing provider takes effect on the next message and after Save, without a reload.
  • The configured command is used verbatim as argv tokens; shell strings and quotes remain rejected. Defaults are now one-shot, JSON-capable commands for all four providers.
  • The CLI may spend real tokens and may fail. Errors surface in the dock; patches still require the existing trust mode and edit/checkpoint path. The agent never writes repository files itself.
  • Mock mode stays deterministic and now labels its output as demo instead of pretending to be a real agent run.
