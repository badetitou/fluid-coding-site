ADR-0031 — fluid MCP tool server over stdio

  • Status: proposed
  • Date: 2026-11-26
  • Deciders: Benoit (to validate)
  • Depends on: ADR-0030 (local API origin policy, proposed), ADR-0033 (single analysis engine, proposed)

Context

ADR-0005 and AGENTS.md rule 5 say agents are guests: Claude Code, opencode, Codex and Pharo MCP use the same MCP tools, and the in-app agent runs behind AgentPort (crates/fluid-core/src/plugins/agent.rs). No MCP server exists today:

  • packages/contracts/src/mcp-tools.ts defines zod schemas for 11 tools (get_matrix, cell_symbols, get_entity, get_relations, get_impact, get_diff, list_tags, propose_tag, list_tasks, get_task, task_brief); no Rust struct backs them, and there is no propose_patch tool.
  • apps/web/src/lib/agents.ts hardcodes mcpToolCatalog (8 entries) and AgentsPage.tsx shows it as if it were served.
  • crates/fluid-server/src/agents/cli.rs splits the configured command on whitespace, appends the prompt as one argv value (no shell) and sets the cwd (the task worktree, ADR-0029). The prompt tells the agent to “Use the read-only MCP tools for facts” — none are passed.
  • The facts already exist behind loopback HTTP routes: /api/matrix, /api/entity/{key}, /api/relations/{key}, /api/impact, /api/tags. Patch proposals live only in fluid-server memory (state.inner.patches), registered by POST /api/edits/propose, which never applies. POST /api/tags upserts any status, including accepted.
  • Crate graph: fluid-cli (binary fluid-coding) → fluid-server → fluid-index → fluid-core.
  • The official Rust SDK is rmcp (modelcontextprotocol/rust-sdk). cargo search rmcp on 2026-11-26 reports rmcp = "3.11.0" and rmcp-macros = "3.11.0". Features (server, transport-io, client, transport-child-process, schemars integration) must be confirmed against that version’s docs when the crate is added.

Decision

  1. Transport: stdio first. Every target CLI spawns local MCP servers as child processes over stdio. Streamable HTTP is a later step, mounted on fluid-server only once ADR-0030’s origin/token policy is accepted and implemented; it reuses the same tool registry.

  2. Location: new crate fluid-mcp, exposed as fluid-coding mcp. fluid-mcp is a library (rmcp server, tool registry wiring, HTTP client) depending on fluid-core only for wire types. fluid-cli gains an mcp subcommand that calls fluid_mcp::serve_stdio(options) and returns before any window, asset extraction or server bind. fluid-server’s dev binary gets the same subcommand so cargo run -p fluid-server -- mcp works without packaging. One installed executable serves the app and the MCP bridge; no second binary to ship or sign.

  3. State: the bridge proxies the running fluid-server; it does not load the index.

    Proxy loopback HTTP (chosen) Read index directly (fluid-mcp → fluid-index)
    Source of state one: the app’s warm index, tags, proposals a second copy that can diverge
    Writes through /api/edits/propose, visible in Review at once cannot reach in-memory proposals
    Cold start process spawn + one HTTP call full fluid_index::load per agent run
    Standalone use needs the app running works without the app
    The server URL and a per-run token are passed as fluid-coding mcp --server <url> --run <id>
    (token via env FLUID_MCP_TOKEN, never argv). For a CLI launched by hand, the bridge reads
    .fluid-coding/server.json (gitignored, written by the server on bind: url, pid). If no server
    answers, tools return a typed MCP error “fluid-coding is not running”, never stale data. A
    read-only direct-index mode is explicitly deferred.

  4. v1 tools and access. The registry is a Rust table in fluid-core (McpToolDescriptor { name, summary, access, params }), pure data, wasm-safe. Inputs/outputs are serde structs in fluid-core; JSON Schema for tools/list is derived from them (schemars), and mcp-tools.ts becomes generated per ADR-0034.

    Tool Access Backed by
    get_matrix read GET /api/matrix
    cell_symbols read Miller/cell route (add a paginated route if missing)
    get_entity read GET /api/entity/{key}
    get_relations read GET /api/relations/{key}
    get_impact read GET /api/impact; engine per ADR-0033
    propose_patch write-propose POST /api/edits/propose (new contract entry)
    propose_tag write-propose new POST /api/tags/propose, forces status: proposed
    No tool applies a patch, restores a checkpoint, accepts a tag or writes files. propose_tag gets
    its own route because the generic POST /api/tags accepts accepted; the server, not the bridge,
    enforces “proposal only”. Proposals carry the run id so ADR-0029’s worktree root and task key are
    attached server-side. get_diff, list_tags, list_tasks, get_task, task_brief follow in
    v1.1 once their Rust structs exist. get_impact ships with whatever /api/impact serves; its
    output shape is fixed now, so ADR-0033 changes the engine, not the tool.

  5. Config injection: one adapter per provider, written to a run file. A typed McpInjector per agent manifest (rule 9) turns {exe, args, env} into extra argv/env for cli.rs; no special case in routes. The config file goes to .fluid-coding/runs/<run>/mcp.json; the user’s ~/.claude.json, ~/.codex/config.toml or repo opencode.json are never edited. Argv is still built without a shell.

    • Claude Code (known): --mcp-config <file> --strict-mcp-config, plus --allowedTools mcp__fluid__* so -p runs are not blocked on permission prompts. Verify flag names on the installed version.
    • Codex (to verify): codex exec -c 'mcp_servers.fluid.command="…"' -c 'mcp_servers.fluid.args=[…]' (TOML dotted overrides of [mcp_servers]).
    • opencode (to verify): an mcp.fluid = { type: "local", command: [...] } entry in a config pointed to by OPENCODE_CONFIG (or OPENCODE_CONFIG_CONTENT if supported).
    • Ollama / in-app provider: no MCP client; the Fluid Agent calls the same registry in-process. An unknown provider runs without tools and the run records a warning; it never fails silently.

  6. Catalog from the server. GET /api/agents/tools returns the fluid-core registry plus a served: bool per tool. The Agents screen fetches it; mcpToolCatalog is deleted from apps/web and packages/contracts. A Rust test asserts the bridge’s tools/list names equal the registry.

  7. Testing. Unit: registry ↔ contract names; each tool maps its input to the right route (mock HTTP). Integration (crates/fluid-mcp/tests/stdio.rs): start fluid_server in-process on an ephemeral loopback port over a fixture workspace, spawn fluid-coding mcp with rmcp’s child-process client, call tools/list and get_matrix, and compare with fixtures/contracts/mcp/get_matrix.json, which Vitest also parses with the zod schema. A propose_patch test asserts the proposal appears in GET /api/edits and no file changed. Dogfood: a real claude -p run on fluid-coding calls mcp__fluid__get_matrix.

Consequences

Positive:

  • Rule 5 becomes true: external CLIs and the in-app agent share one registry and one state.
  • Agent writes land as reviewable proposals; trust modes and checkpoints stay the only apply path.
  • No new long-lived process and near-zero cold start per agent run.
  • The Agents screen shows what is actually served.

Negative:

  • MCP tools only work while the app (or fluid-server) runs; a hand-launched CLI without the app gets a clear error, not data.
  • The bridge depends on loopback HTTP being reachable by a non-browser client: ADR-0030 must allow token-authenticated requests without an Origin header.
  • Three provider-specific injectors to maintain, two of them not yet verified on real binaries.
  • rmcp (plus schemars, if needed) is a new dependency with frequent major versions; pin exactly.

Alternatives considered

  • fluid-mcp → fluid-index reading the index directly. Rejected for v1: duplicated state, full index load per run, and writes could not reach the server’s in-memory proposals.
  • MCP subcommand inside fluid-cli without a crate. Rejected: fluid-cli is the app shell (window, assets); the protocol code would bloat it and be untestable without the shell.
  • Streamable HTTP first. Rejected: needs ADR-0030 first, and every target CLI supports stdio.
  • Editing each CLI’s global config. Rejected: mutates user files outside the repo and leaks fluid tools into unrelated sessions.
