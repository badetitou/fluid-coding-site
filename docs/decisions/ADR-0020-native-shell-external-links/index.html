ADR-0020 — The native shell hands external links to the OS

  • Status: accepted
  • Date: 2026-11-25

Context

The macOS app hosts the UI in WKWebView. WKWebView keeps target="_blank" links and custom schemes inside the webview unless the host intercepts them. Clicking Open GitHub, Open GitLab, a task URL or the vscode://file/... escape hatch therefore did nothing visible: the verification page never reached the user’s default browser.

The web layer must stay a presentation layer; it cannot ask the OS to open a URL. The launch decision belongs to the native shell that already owns the window.

Decision

crates/fluid-cli/src/native.rs registers two WKWebView handlers:

  • with_navigation_handler intercepts same-window navigations;
  • with_new_window_req_handler intercepts target="_blank" and window.open requests.

A URL is external when it uses https:, http: or vscode: and is not on the local server origin. External URLs are passed to the OS launcher (open on macOS, cmd /C start on Windows, xdg-open elsewhere) and the webview navigation is denied. The local origin is matched on a path, query or fragment boundary so a host such as 127.0.0.1:<port>.evil.example is never mistaken for the app.

Consequences

  • Forge verification, issue links and the VS Code escape hatch open in the user’s default handlers, including when the app is installed and no terminal is attached.
  • In-app routes keep working because the local origin is excluded.
  • The launcher is invoked with an argument vector, never through a shell, so a link cannot become a command. Non-HTTP schemes are deliberately limited to vscode:.
  • The behaviour is unit-tested on the URL classifier; the OS handoff itself needs a manual check on a built app.
