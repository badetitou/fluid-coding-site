ADR-0017 — GitHub device flow and open issues as tasks

  • Status: accepted
  • Date: 2026-11-25
  • Amended by: ADR-0018, ADR-0019

Context

ADR-0016 kept forge auth PAT-only and left oauth_device for future work. Users should not have to create and paste a token: they should approve fluid on GitHub in the browser. A local desktop app cannot receive an OAuth redirect without a callback server and a client secret, so the device flow is the right fit: the user types a short code on github.com, and the server polls until approval.

Decision

  • GitHub sign-in uses the OAuth device flow. The client id is read from FLUID_GITHUB_CLIENT_ID. No client secret is used or stored. The base URL is https://github.com (GitHub Enterprise is not covered yet).
  • The OAuth token is stored like a PAT: a 0600 file in the forge store, never returned by any response. The account has authMethod: oauth_device. A second sign-in as the same user replaces the token of that account.
  • Scope is repo, so private repositories’ issues are readable. This is broader than issue-only access; narrowing it is a follow-up once we know which repos matter.
  • Open issues of the active repo’s origin (GitHub only) are merged into GET /api/tasks while a device-flow account exists. A failed fetch is an error response, never an empty board. Only the first page (100 issues) is fetched; pull requests are dropped.
  • Endpoints: POST /api/forge/github/device starts the flow; POST /api/forge/github/device/{id} polls it. The poll handle is opaque, random, and bound to the server-side device code.
  • GitLab is covered separately by ADR-0018.

Consequences

  • An OAuth App with device flow enabled had to be registered on GitHub. ADR-0019 supersedes the environment-variable configuration: its public client id is now bundled in the app.
  • The task board calls GitHub on every /api/tasks read while connected. There is no cache yet.
  • Issue briefs for GitHub tasks are not generated (/api/tasks/{key}/brief only knows local tasks).
  • Starting work on a GitHub issue uses its branch name only if the issue carries one: GitHub issues have no branch field, so branch_name derives one from the task.
