ADR-0015 — First-run project setup by guided form or chat

  • Status: accepted
  • Date: 2026-11-25

Context

A new user opens fluid-coding and the first question is not “what do I review?” but “how do I tell you where my project lives?”. Today this requires knowing .fluid-coding/project.json, the plugin manifests and the repo layout (ADR-0014). That is too much friction for a prerelease tester.

The user should be able to say “I want to work on project X at ~/dev/x” in a chat, or fill a short form with checkboxes and dropdowns, and get a concrete, reviewable setup.

Decision

Add a first-run Setup surface at /setup. When the local project index is empty, the CLI opens the browser on /setup instead of /. Setup can always be reopened from Settings.

Two input modes produce the same SetupRequest:

  • guided: name, root path, repository rows, language checkboxes, plugin checkboxes, trust mode;
  • chat: free text, optionally with a path; parsed by a SetupPort adapter.

SetupPort is a new typed port in fluid-core, next to AgentPort and NarrativePort. It returns a SetupProposal, never a write. The proposal is validated JSON:

SetupProposal {
  source: 'deterministic' | 'llm' | 'mixed',
  project: { name, root },
  repos: [{ repoKey, path, languages: string[] }],
  plugins: [{ id, enabled, reason }],
  trust: 'propose' | 'edit' | 'auto',
  taskProvider?: 'local' | 'github' | 'gitlab',
  questions: string[],
  warnings: string[]
}

The deterministic adapter scans the given directory (.git, package.json, tsconfig.json, pom.xml, *.tonel, README) and the plugin registry, then proposes repos, languages and plugins. It works offline and is the default. An LLM adapter may enrich the same proposal by extracting the project name, path and intent from chat; its output is validated with zod/serde and merged with the deterministic result. As with narrative, the LLM is enrichment, never evidence: a missing or invalid LLM response must not block setup.

Applying a proposal is explicit: POST /api/setup/apply writes .fluid-coding/project.json, updates ~/.fluid-coding/projects.json and activates the project. Defaults stay trust: propose, and setup never writes source files. A proposal that asks for workspace:write, network:out or process:spawn permissions lists them in the review step and requires a separate checkbox.

Safety rules:

  • a path from chat is treated as untrusted text: it must resolve to an existing directory;
  • the LLM never receives shell execution and never supplies raw file content;
  • questions and warnings are surfaced in the UI, not silently resolved;
  • plugin ids in a proposal are checked against the registry, so a hallucinated plugin is rejected;
  • a failed apply leaves the previous project index untouched (write to a temp file, then replace).

The setup UI follows the plugin-first rule: it renders manifests from the registry and does not hard-code a list of plugins or languages. The guided form and the chat are two front doors to the same proposal and review component.

Consequences

  • Testers can go from a fresh app to an active project in one screen.
  • Multi-repo projects are described at setup time, so ADR-0014 lanes are populated from the start.
  • Plugin discovery and setup hints come from the registry; no ad-hoc plugin list in the UI.
  • LLM output is optional and validated, keeping the local-first, offline-capable contract intact.
  • The CLI needs to choose the startup route from the project index; a projectless launch opens /setup.
  • First-run setup is a separate port with its own contract tests, not an ad-hoc route handler.
