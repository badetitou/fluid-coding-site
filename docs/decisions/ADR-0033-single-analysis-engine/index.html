ADR-0033 — One analysis engine: the Model computes, fluid-core projects

  • Status: proposed
  • Date: 2026-11-26
  • Deciders: Benoit

Context

Two graph engines live side by side and only one is wired:

  • fluid-core::analyze_impact (crates/fluid-core/src/impact.rs) is a cell-level BFS. It maps changed files and symbols to matrix cells through CellIndex, reverses every relation kind into cell → cell edges, and walks at most max_depth (3) cell hops. AppState::load runs it once per generation; GET /api/impact returns the cached Impact (changedCells, impactedCells[{id, distance}]). The web app (serverWorkspace.ts), the change brief and fixtures/contracts/impact.json all read that shape.
  • fluid-index::model_bridge (analyze, analyze_with_depth, analyze_with_seeds) freezes the CodeGraph into a model_core::Model and delegates cycles and propagation to model-analysis 0.8 (crates.io, model-core + serde + anyhow, no I/O). Its propagation is entity-level, follows only Calls + References, and counts entity hops. It has no caller. docs/architecture-model-bridge.md already names badetitou/model the canonical engine.

model-analysis 0.8 also ships Degree, Unused, Metrics and Quotient, none exposed yet. The Home “Checks” card announces cycles that nothing computes.

crates/fluid-wasm exports analyze_impact_json, but no package or app imports fluid-wasm today: the browser receives impact only from the server.

The matrix spec is not configurable. fluid-index/src/matrix_spec.rs reads no file: layers are the first directory under the repo (src, apps, crates, …) and domains are the repo name, which gives fluid-coding itself four cells. There is no .fluid/ directory in the repository.

Decision

  1. The Model is the only graph-analysis engine. Cycles, degrees, unused entities and impact propagation run in model-analysis, called from fluid-index (the adapter layer). fluid-core keeps what is not graph analysis: CodeGraph, MatrixSpec/CellIndex, build_matrix, change briefs and the wire types Impact, ImpactRequest, ImpactedCell.

  2. /api/impact keeps its contract. Its shape and its cell-hop semantics stay as today. The index builds a second, cell-level Model (one entity per cell, one relation per distinct cell → cell dependency of any kind, as reverse_cell_edges does now) and runs model_analysis::Propagation with Direction::Callers and max_depth from the request. The result is projected back into Impact. Entity-level propagation (analyze_with_seeds) stays a separate answer, served by the analysis route, not mixed into cell distances. Rationale: projecting entity distances onto cells (minimum per cell) would change the numbers users see, because depth 3 in entity hops reaches far fewer cells than depth 3 in cell hops, and it would drop Inherits/Imports/Contains edges the current BFS follows.

  3. fluid-core::analyze_impact is removed once (2) lands with a parity test, together with analyze_impact_json in fluid-wasm. The wasm facade has no consumer, so nothing breaks. If an offline wasm worker needs impact later, fluid-wasm may depend on model-analysis directly (it has no I/O dependency); fluid-core does not.

  4. Purity rule stays intact. fluid-core does not depend on model-core or model-analysis. The bridge stays in fluid-index (crates/fluid-server → fluid-index → fluid-core, and fluid-index → model-analysis → model-core). No async, filesystem or process code moves.

  5. Analysis is exposed as data. GET /api/model/analysis returns ModelAnalysis extended with degrees (Degree) and unused entities (Unused), computed once per generation and cached in AppState (rule 5 of the performance doc: cache by (generation, query)). The client renders; it never recomputes.

  6. Layered matrix spec is repository config. fluid-index reads an optional .fluid/matrix.json per repo and falls back to today’s directory buckets when it is absent or invalid (with a warning, never a panic). The file holds MatrixSpec’s layers plus path rules, not per-symbol assignments:

    {
  "layers": [
    { "id": "web-pages",    "label": "apps/web · pages",  "order": 0, "paths": ["apps/web/src/pages/", "apps/web/src/app/"] },
    { "id": "web-features", "label": "apps/web · features/components", "order": 1, "paths": ["apps/web/src/components/", "apps/web/src/layout/"] },
    { "id": "web-entities", "label": "apps/web · data/lib", "order": 2, "paths": ["apps/web/src/data/", "apps/web/src/lib/", "apps/web/src/api/"] },
    { "id": "packages",     "label": "packages",            "order": 3, "paths": ["packages/"] },
    { "id": "server",       "label": "fluid-server",        "order": 4, "paths": ["crates/fluid-server/", "crates/fluid-cli/"] },
    { "id": "index",        "label": "fluid-index",         "order": 5, "paths": ["crates/fluid-index/"] },
    { "id": "core",         "label": "fluid-core / wasm",   "order": 6, "paths": ["crates/fluid-core/", "crates/fluid-wasm/"] }
  ],
  "domains": { "by": "second-segment" }
}

    Longest matching path prefix wins; unmatched files go to a root layer. The output is still a MatrixSpec, so /api/matrix and CodeMatrix are unchanged. This part is not a boundary change: it applies ADR-0004 (rules and views are plain files in .fluid/) and may ship before this ADR is accepted.

What can ship before acceptance

  • GET /api/model/analysis (cycles, cyclicEntities, entity propagation, degrees, unused), its zod contract and shared fixture, and the Structure “Analysis” section. This only exposes the existing bridge; it does not change which engine serves /api/impact.
  • .fluid/matrix.json reading and the repo’s own file (test: fluid-coding has more than 4 cells).
  • A criterion bench for analyze_impact and for the bridge on the same graph, to record the baseline docs/quality/performance.md still lists as “not measured yet”.

What waits for acceptance

  • Switching /api/impact to the cell-level Model propagation (decision 2).
  • Removing fluid-core::analyze_impact, its tests and fluid-wasm::analyze_impact_json (decision 3), and updating docs/architecture-model-bridge.md “Compatibility”.

Consequences

Positive:

  • One implementation of cycles and propagation; the Checks card and MCP get_impact read the same numbers as the Structure page.
  • The /api/impact wire contract and fixtures/contracts/impact.json stay valid; a parity test compares the old BFS and the Model on the fixtures before the old one is deleted.
  • fluid-core stays pure and wasm-buildable with no new dependency.

Negative:

  • Each generation now builds two Models (entity-level and cell-level) on top of the CodeGraph and the matrix. That is extra memory against the 300 MB / 1M LOC budget and extra time against “Impact, 100k LOC graph p95 < 100 ms”. The switch in decision 2 is gated on a bench that stays under that budget; if it does not, impact stays in fluid-core and this ADR is revised.
  • fluid-coding depends on model-analysis semantics and release cadence (0.8 on crates.io). A breaking upstream change must be absorbed in model_bridge.rs only.
  • Offline (wasm-only) impact is no longer available from fluid-core; it is not used today.

Alternatives considered

  • Keep fluid-core’s BFS as the only engine and delete the bridge. Rejected: it duplicates what the canonical Model already does and would need its own cycles, degrees and unused analyses.
  • Serve /api/impact from entity-level analyze_with_seeds projected to cells. Rejected for now: it silently changes distances and the set of followed relation kinds (see decision 2).
  • Move model-analysis into fluid-core. Rejected: it couples the pure core to an external release train; the adapter layer is where the bridge belongs.
