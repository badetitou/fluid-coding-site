ADR-0019 — Bundled forge OAuth client ids

  • Status: accepted
  • Date: 2026-11-25
  • Amends: ADR-0017, ADR-0018

Context

ADR-0017 and ADR-0018 made the Tasks page sign-in buttons work through the OAuth device flow, but read the client ids from FLUID_GITHUB_CLIENT_ID and FLUID_GITLAB_CLIENT_ID. The installed .app has no environment configuration, so both buttons failed with “sign-in is not configured” even though the device flow itself was implemented. Asking testers to export variables defeats the point of a local app.

Decision

  • The public client ids of the fluid-coding OAuth apps are compiled into crates/fluid-server/src/forge/client_ids.rs. They identify the app to the forge; they are not secrets, and no client secret is stored anywhere.
  • ForgeService::new uses the bundled id unless the corresponding FLUID_* variable is set and non-empty. GitLab defaults to https://gitlab.com; FLUID_GITLAB_URL still selects a self-managed instance.
  • Both device flows keep their existing behaviour: the browser receives only the user code and a public account, and the access token stays in the 0600 forge token store.
  • The “not configured” error now describes a build without an id rather than telling the user to set an environment variable. It is unreachable in released builds and remains useful for tests.

Consequences

  • The sign-in buttons work out of the box in the installed app. The OAuth apps are registered under the project owner’s GitHub and GitLab accounts; rotating them means rebuilding the binary.
  • Private deployments can still point at their own OAuth app with an environment override, which is optional rather than required.
  • Embedding a client id widens its exposure, which is safe: an OAuth client id is public data, and device flow needs no secret. Scopes stay repo (GitHub) and read_api (GitLab), both read-only in fluid-coding.
  • A live approval still needs a logged-in forge account; the automated coverage exercises both device flows against local HTTP doubles and checks the bundled-id fallback.

Dogfood note

This repository is the active project used for the checks. Live POST /login/device/code (GitHub) and POST /oauth/authorize_device (GitLab) calls with the bundled ids both returned a user code and verification URL. The GitLab application first rejected the request until its Device grant type was enabled; the server now names that setting in the error for future self-managed deployments. Both flows are exercised through local HTTP doubles in the test suite, and the full Rust test/clippy gate passes. An end-to-end approval still needs a browser signed in to the forge, which the agent does not have.
