ADR-0030 — Local API origin and Host policy

  • Status: accepted
  • Date: 2026-11-26
  • Deciders: Benoit (accepted by the orchestrator on his behalf)

Context

The local server is bound to loopback only: fluid-server reads FLUID_ADDR (default 127.0.0.1:4200) and refuses a non-loopback address (crates/fluid-server/src/main.rs:16-20); the desktop CLI binds 127.0.0.1 on --port (default 4200) and tries the next 19 ports if busy (crates/fluid-cli/src/server.rs:16-30, crates/fluid-cli/src/args.rs:12). The resolved port is exported as FLUID_OTLP_PORT (crates/fluid-cli/src/main.rs:45) and read back by telemetry::env::endpoint_port(), which falls back to FLUID_ADDR, then 4200.

Loopback binding does not protect against the browser. The router is wrapped in CorsLayer::permissive() (crates/fluid-server/src/lib.rs:58). Verified with curl:

  • OPTIONS /api/settings/general with Origin: https://evil.example answers access-control-allow-origin: * and access-control-allow-methods: *, so any web page the user visits may call the API and read the answer.
  • GET /api/health with Host: evil.example:4200 answers 200 with repository data: a DNS-rebinding page can talk to the server as a same-origin client.

The API mutates the repository and runs processes: POST /api/edits/{id}/apply, POST /api/checkpoints/{id}/restore, PATCH /api/settings/general (sets the agent command line), POST /api/agents/{id}/run, and /api/forge/* (forge tokens and issue creation). A “simple” cross-origin POST is executed even when the browser later hides its response.

How the UI is loaded: the macOS shell builds http://127.0.0.1:<bound port> (crates/fluid-cli/src/main.rs:41) and opens it in a wry WKWebView with .with_url(url) (crates/fluid-cli/src/native.rs:109). There is no custom scheme; the desktop origin is the server origin itself. Other platforms open the same URL in the default browser (main.rs:65). In development, Vite serves the UI on http://127.0.0.1:4100 and proxies /api to http://127.0.0.1:4200 without changeOrigin (apps/web/vite.config.ts:8-10), so proxied requests keep Host: 127.0.0.1:4100 and browser requests carry Origin: http://127.0.0.1:4100.

Decision

A new module crates/fluid-server/src/security.rs owns one pure policy plus one axum middleware. lib.rs replaces CorsLayer::permissive() with it; handlers in routes/ are not touched. The port P is the bound port, passed to demo_app(port); the CLI builds the router after it binds.

  1. Allowed origins (exact, scheme + host + port):
    • http://127.0.0.1:P, http://localhost:P, http://[::1]:P. The desktop WKWebView uses the first, so it needs no extra entry.
    • Development origins from FLUID_DEV_ORIGINS, a comma-separated list of exact origins (for example FLUID_DEV_ORIGINS=http://127.0.0.1:4100,http://localhost:4100). Empty by default; never hard-coded. Malformed entries are ignored with a tracing warning.
  2. CORS: a CorsLayer with an AllowOrigin::predicate over the allowed origins, explicit methods and headers, no credentials. A foreign Origin gets no access-control-allow-origin header.
  3. Host validation: the Host header must be 127.0.0.1:P, localhost:P or [::1]:P, or the host:port of a FLUID_DEV_ORIGINS entry (needed for the Vite proxy). Anything else, including a missing Host or a loopback name on another port, gets 403 before routing. This closes DNS rebinding.
  4. Unsafe methods: a request whose method is not GET, HEAD or OPTIONS and that carries an Origin not in the list gets 403 without reaching the handler, even though the browser would have blocked the response. Origin: null is treated as foreign.
  5. No Origin: requests without Origin (curl, scripts, agent CLIs) pass the origin check; they are not browser cross-origin requests. Host validation still applies. This is what keeps POST /_telemetry/v1/traces working: provider SDKs post OTLP JSON to http://127.0.0.1:P/_telemetry/v1/traces with a loopback Host and no Origin. A test covers it explicitly.
  6. Static files (fallback_service) go through the same Host check; they are GET, so the origin rule does not apply to them.
  7. Tests first, in fluid-server: foreign Origin → no allow-origin header; foreign Host → 403; foreign-Origin POST → 403 and handler not called; allowed origin → normal answer and header; dev origin via FLUID_DEV_ORIGINS → accepted; OTLP POST without Origin → accepted. The policy is a pure function over (method, host, origin, port, dev list) and is unit-tested.

Consequences

Positive:

  • Any web page, and any DNS-rebinding page, loses read and write access to the local API.
  • The desktop shell and the built web UI keep working unchanged: they are same-origin.
  • One small module, no change to route handlers, no new dependency (tower-http already provides CorsLayer).

Negative and not covered:

  • Development behind pnpm dev: the Vite proxy sets changeOrigin: true, so the Host the server sees is its own and GETs work. Browser writes still carry Origin: http://127.0.0.1:4100, so cargo run -p fluid-server needs FLUID_DEV_ORIGINS=http://127.0.0.1:4100 (or the localhost form); without it every write from the dev UI gets 403. Docs must say so.
  • The port P is passed explicitly by the process that binds (demo_app(port)), never read from inherited environment such as FLUID_OTLP_PORT; the CLI therefore builds the router after the bind.
  • Local processes on the same machine are trusted: any process that can open a loopback socket can call the API with no Origin and a loopback Host. That includes other users’ processes on a shared machine.
  • There is no authentication. A per-launch bearer token (generated by the CLI, injected into the WKWebView and the spawned agents’ environment, required on mutating routes) is the likely next step and would need its own ADR.
  • Browser extensions and native apps that forge headers are out of scope.
  • If the port changes at runtime (it does not today), the cached P must be refreshed.

Alternatives considered

  • Keep CorsLayer::permissive() and rely on loopback binding. Rejected: proven exploitable from any web page through CORS and DNS rebinding.
  • Custom URL scheme for the desktop shell. Rejected for now: the shell works with plain loopback HTTP and a scheme would add a second origin to allow without removing the first.
  • Token-only protection. Deferred: it does not stop DNS rebinding reads of unauthenticated GETs unless every route requires it; Host validation is needed either way.
