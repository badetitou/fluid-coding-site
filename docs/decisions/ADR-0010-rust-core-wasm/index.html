ADR-0010 — Rust-first backend, shared WASM core, performance

  • Status: accepted
  • Date: 2026-11-25
  • Deciders: Benoit, fluid-coding team

Context

fluid-coding must index real repositories, compute structural impact, serve tags and changes, and stay interactive while an agent is working. The first scaffold used a TypeScript/Fastify backend because it matched fluid. That shape adds a Node runtime, a second type system, and a slow path for the hot graph operations. The product also needs an online mode without maintaining a separate implementation.

Decision

  1. Rust owns the backend. fluid-server uses axum/tokio; indexing, git, watchers and MCP are Rust.
  2. Pure core. fluid-core contains graph, matrix, impact, tags, briefs and risk. It has no I/O, no async runtime and no clock. It compiles to native and wasm32-unknown-unknown.
  3. WASM for online. fluid-wasm is a thin wasm-bindgen facade. It powers the browser/edge read-only mode and off-main-thread computation. Native and wasm use the same JSON contracts.
  4. TypeScript is presentation. The React shell renders typed JSON, does local filtering and virtualization, and never recomputes graph semantics.
  5. Performance is a release gate. The budgets in docs/quality/performance.md are enforced in CI; a regression blocks the release.

Consequences

Positive:

  • One implementation of the graph and impact logic across local, hosted and wasm modes.
  • Predictable memory and latency; no GC pauses on the index path.
  • A single installable binary is realistic (fluid-cli embeds the web assets).
  • WASM components are also a natural sandbox for third-party analyzers.

Negative:

  • Two toolchains (Cargo + pnpm) and a generated contract step.
  • Rust iteration is slower for UI-adjacent work; keep experiment code out of fluid-core.
  • WASM target checks must be in CI or the core will accidentally depend on std I/O.
  • The team needs Rust fluency; pair on adapters and keep core small.

Alternatives considered

  • TypeScript/Fastify everywhere. Fast to start, but two type systems, slower graph work and a weak single-binary story. Rejected.
  • Rust for indexing only, Node API. Keeps the Node ecosystem but adds IPC and two deployments. Rejected; the API is small enough to own in Rust.
  • Go backend. Good latency and deployment, but no shared browser/wasm core and weaker type-level modelling for the graph. Rejected.
  • WASM-only. Cannot own files, git or agent processes. Rejected as the only mode; kept as online.

Migration

The TypeScript contracts and mock server remain during P0 as fixtures. The Rust core is authoritative as soon as the first endpoint is wired. No production data exists yet; no migration is required.
