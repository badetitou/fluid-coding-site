ADR-0037 — The tool catalogue comes from the running server

  • Status: accepted
  • Date: 2026-11-26
  • Deciders: Benoit
  • Depends on: ADR-0031 (fluid MCP tool server, proposed), ADR-0034 (generated contracts, proposed)

Context

The Agents screen showed eight tools from apps/web/src/lib/agents.ts, a hand-written list with no server behind it. packages/contracts/src/mcp-tools.ts declares eleven aspirational tools, including cell_symbols and get_diff, and no Rust code implements or serves them. There is no MCP server in crates/ yet: the facts available to an agent are the loopback HTTP routes of fluid-server (/api/matrix, /api/entity/{key}, /api/relations/{key}, /api/impact, /api/changes, /api/checks, /api/tags, /api/tasks*, /api/edits*), plus real write routes for tags and patch proposals. A UI list that claims more than the server delivers is misinformation, and two hand-written lists will drift.

ADR-0031 defines the future MCP registry and endpoint (GET /api/agents/tools with a served flag). That bridge does not exist; shipping its aspirational table now would repeat the same mistake under a different name.

Decision

  1. The catalogue is pure data in fluid-core. crates/fluid-core/src/tools.rs defines ToolDescriptor { name, summary, access: read | write, params } and a const TOOL_CATALOG containing only tools backed by a route registered in fluid-server/src/routes/mod.rs. access is write only where a real write route exists (POST /api/tags, POST /api/edits/propose); propose_patch explicitly does not apply the patch. No I/O, runtime or async code enters the core, which still builds for wasm32-unknown-unknown.

  2. The server publishes that table. GET /api/tools serializes Vec<ToolDescriptor> in camelCase from fluid-server/src/routes/tools.rs. There is no served flag: by construction every entry is served today. When a route disappears, its descriptor goes with it.

  3. The contract is mirrored and pinned by a shared fixture. packages/contracts/src/tools.ts holds the zod schema used to validate the untrusted HTTP response, with explicit TypeScript types. fixtures/contracts/tools.json is parsed by a Vitest test and compared byte-for-byte (as JSON values) with the Rust table in both the core and the route tests. Names stay unique, and the write set stays exactly the two routes above.

  4. The web client fetches, never invents. codingApi.tools() calls /api/tools and parses it with zod; in mock mode, where no server exists, it honestly returns an empty list. A typed useToolCatalog() hook feeds the Agents screen, which shows a fetch error or an explicit empty state instead of a fallback catalogue. apps/web/src/lib/agents.ts is deleted, including its invented provider-status and trust-mode tables.

  5. Aspirational schemas stay out of the UI. mcp-tools.ts keeps its input/output schemas for the future MCP bridge, but nothing renders them as available tools. Adding an entry there does not add an entry to TOOL_CATALOG; that requires a served route and this ADR’s fixture update.

Consequences

Positive:

  • Agents sees exactly what the current server can do; no offline or stale UI list can overclaim.
  • One Rust-owned table feeds the HTTP response, the Rust tests and the TS fixture.
  • Removing the hard-coded file also removes fabricated provider connectivity and trust labels.

Negative:

  • The catalogue is only as complete as the route-to-tool mapping; new routes do not automatically become tools, by design.
  • The zod schema duplicates the Rust shape until ADR-0034’s generator is in place; the shared fixture and the satisfies z.ZodType<ToolDescriptor> check limit drift.
  • When ADR-0031’s MCP bridge lands, the endpoint and served flag must be reconciled with this one; the registry data stays in fluid-core.

Alternatives considered

  • Render mcp-tools.ts names in the Agents screen. Rejected: none is served by Rust today.
  • Add a served flag now and copy the aspirational list. Rejected: the UI would still present unavailable capabilities and two lists would need manual synchronisation.
  • Keep the web catalogue with a runtime capability probe per tool. Rejected: N+1 requests and a second, private definition of the server’s surface.
