ADR-0034 — TypeScript contracts are generated from Rust wire structs

  • Status: proposed
  • Date: 2026-11-26
  • Deciders: Benoit

Context

AGENTS.md rule 6 says wire types are Rust structs with serde, TypeScript types are generated, and zod validates only untrusted input. Today none of that is generated:

  • packages/contracts/src/ holds 16 hand-written zod modules (~2,200 lines, ~190 exported schemas): agents 26, mcp-tools 27, forge 21, project 18, setup 15, tasks 13, code-graph 13, edit 12, session-graph 10, settings 8, tags/language-provider/workspace 7, change-brief 5, theme 3. Every TS type is z.infer<typeof …Schema>, so the schema is the type.
  • The Rust side has ~150 Serialize structs/enums: ~130 in fluid-core (tasks, plugins/edit, plugins/forge, plugins/agent, sessions, setup, projects, session_graph, matrix, impact, tags…), ~19 in fluid-server (settings model/view, projects, forge device flow, some route DTOs) and 4 in fluid-index. Drift between the two sides is caught only where a fixture exists.
  • fixtures/contracts/ has 10 files. All are parsed in fixtures.test.ts/domain tests on the TS side; only 4 (chat-sessions, project, setup, session-graph) are also read by Rust tests via include_str!. matrix, impact, tags, tasks, forge and change-brief are TS-only.
  • Serde usage that a generator must honour: rename_all = "camelCase" (most types, plus lowercase ×10, snake_case ×10, kebab-case ×1), default (~180), default + skip_serializing_if (68), one internally tagged enum (setup/types.rs, tag = "mode"), one untagged enum (TagValue), one flatten (server routes/miller.rs), 6 serde_json::Value fields and 25 u64/i64/usize fields.
  • apps/web/src/api/* parses every response with zod (~45 parse calls). The server is ours, but the desktop shell has served a stale web bundle against a newer server (fixed in 3e2cb08), and a dev server may be a different build: responses are a real process boundary.
  • fluid-core must stay pure and build for wasm32-unknown-unknown; fluid-wasm returns JSON strings of the same core structs.

Decision

  1. Tool: ts-rs. It is the most used and longest-maintained serde→TS generator, emits plain .ts type declarations (no runtime), reads serde attributes (rename_all, rename, tag, untagged, flatten, skip, default) and exports from cargo test without a bin. Integer fields default to bigint; we set #[ts(type = "number")] on the 25 wide-integer fields (all are counts, sizes or issue numbers well below 2^53). Option<T> with skip_serializing_if becomes field?: T via #[ts(optional)]; serde_json::Value maps to JsonValue.
  2. Derives live next to the struct, behind a cargo feature ts in each crate that owns wire types (fluid-core, fluid-server, fluid-index only if needed): ts-rs = { workspace = true, optional = true }, [features] ts = ["dep:ts-rs"], #[cfg_attr(feature = "ts", derive(ts_rs::TS), ts(export))]. Without the feature nothing is compiled, so default builds, the wasm check and fluid-wasm are unchanged. ts-rs has no runtime I/O; the file writes happen only in the generated export_bindings_* tests.
  3. Output: packages/contracts/src/generated/, one file per type, committed, header // generated by ts-rs — do not edit, re-exported from src/generated/index.ts (written by the gen script). Hand-written modules import types from there; index.ts keeps its public names.
  4. Command: pnpm contracts:gen (root script) runs node scripts/contracts-gen.mjs, which: empties generated/, runs TS_RS_EXPORT_DIR=packages/contracts/src/generated cargo test --features fluid-core/ts,fluid-server/ts export_bindings, writes the barrel index.ts in sorted order, and runs pnpm --filter @fluid-coding/contracts typecheck. Output is deterministic.
  5. CI drift check: a step in the Rust job of ci.yml runs pnpm contracts:gen then git diff --exit-code -- packages/contracts/src/generated. A struct change without regenerated types fails CI.
  6. “zod only for untrusted input”, concretely.
    • Untrusted = data entering TS from outside the bundle: HTTP/SSE responses read in apps/web/src/api, localStorage, URL params, user-typed forms, pasted/imported JSON, and the JSON strings returned by fluid-wasm. These keep a zod schema.
    • Trusted = values built in TS and passed between modules, request bodies we construct, props. These use the generated type only; no schema.parse on our own outgoing request bodies.
    • Types are never derived from zod again: no z.infer exports. Each schema is checked against the generated type: export const taskSchema = z.object({…}) satisfies z.ZodType<Task>; plus one type test per domain, expectTypeOf<z.output<typeof taskSchema>>().toEqualTypeOf<Task>(), so the schema cannot be looser or stricter than the Rust struct.
    • Response schemas stay in packages/contracts, not in features, and are parsed once per request in apps/web/src/api (no re-parse downstream).
  7. Fixtures on both sides. Every file in fixtures/contracts/ is deserialized and re-serialized in a Rust test (round-trip equality via serde_json::Value) in the crate that owns the struct, and parsed by the matching zod schema in TS. The 6 TS-only fixtures gain Rust tests in their domain PR.
  8. Migration, one PR per domain, each: add derives, regenerate, rewrite the zod module against the generated types, delete hand-written duplicate types, add the Rust fixture test, update docs/contracts/ if an invariant changed.
    • PR 0 — tooling: workspace dep, ts features, contracts:gen, CI drift step, one pilot type (theme), ADR status → accepted.
    • PR 1 — tasks, after W2 merges (ADR-0032 may change the status vocabulary; generating first would mean doing it twice).
    • PR 2 — edits (plugins/edit.rs, patches/checkpoints).
    • PR 3 — agents (plugins/agent.rs, sessions, chat-sessions fixture), after W6 (MCP) lands.
    • PR 4 — forge (plugins/forge.rs + fluid-server/src/forge).
    • PR 5 — settings (fluid-server/src/settings).
    • The W5 analysis contract is not migrated: W5 lands first and its follow-up is generated from day one in PR 0’s tooling (or, if W5 lands after PR 0, W5 uses derives directly).
    • Later, same pattern: setup, project, session-graph, matrix/impact/code-graph, tags, change-brief, language-provider, workspace. mcp-tools.ts (tool input schemas, i.e. untrusted agent input) stays zod and is reviewed separately.

Consequences

Positive:

  • Rust is the single source of wire shapes; TS drift becomes a CI failure, not a runtime surprise.
  • zod shrinks to the boundary: one schema per response type, pinned to the generated type.
  • Every shared fixture is exercised by both serializers, as AGENTS.md already demands.
  • Default and wasm builds carry no new dependency.

Negative:

  • Every wire struct carries a cfg_attr line, and some fields need #[ts(...)] hints (wide integers, optional fields, Value). Forgetting ts(optional) yields T | null instead of T? — caught by the type-equality test, not by Rust.
  • Generating needs a Rust toolchain; a TS-only contributor must run pnpm contracts:gen.
  • zod schemas are still hand-written for response types; the satisfies + toEqualTypeOf pair keeps them honest but is duplication that remains.
  • Generated .ts files add diff noise to contract PRs.

Alternatives considered

  • specta (+ specta-typescript). Better integration story with Tauri/rspc and fine serde support, but v2 spent a long time in release candidates with API churn, refuses u64 unless configured, and needs an explicit export bin/test listing types. ts-rs’s per-type #[ts(export)] fits our “small modules, add a test” style. Revisit if we adopt rspc-style typed procedures.
  • schemars → JSON Schema → zod (json-schema-to-zod). Would also generate the validators, but adds two lossy hops, produces large zod for tagged/untagged enums, ships validators for trusted data, and conflicts with “zod only for untrusted input”.
  • Hand-written TS types with fixture tests only. Status quo; drift is caught only where a fixture exists (4 of 10 on the Rust side).
  • Drop runtime validation of responses (cast to the generated type). Rejected for now: the stale-bundle case is real. Large payloads (matrix, session graph) can revisit this with a measured budget in docs/quality/performance.md.
  • Derives unconditionally (no feature). Simpler, but adds a proc-macro to every build including wasm and fluid-wasm; the feature costs one cfg_attr per type.
