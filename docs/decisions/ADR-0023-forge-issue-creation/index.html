ADR-0023 — Create issues from the Board on the connected forge

  • Status: accepted
  • Date: 2026-11-26
  • Amends: ADR-0011, ADR-0018

Context

ADR-0011 and ADR-0018 made all writes local and kept connected forge issues read-only. The Board already shows local and remote issues in one normalized kanban, but its “New issue” action always created an in-memory local task. A user connected to GitHub or GitLab expects the same action to open a real issue in the active repository, and to fall back to the local kanban when no forge is connected. The repository remains the source of truth: the target comes from the configured project, not from browser-stored credentials.

Decision

  • TaskDraft.source is now auto | local | github | gitlab, defaulting to auto. The Rust wire struct and the zod mirror carry the same enum; the Board form defaults to auto and still offers an explicit target.
  • POST /api/tasks resolves the target server-side from the active project’s origin and settings.taskProviders, using the same GitHub-then-GitLab precedence as snapshot refresh. With a connected account, auto creates the issue on that forge; without one it creates a local task in the todo column. An explicit github or gitlab target reports a typed error when that provider is not connected for the repository; it never silently falls back.
  • Creation uses the token-bearing ForgeService: POST /repos/{owner}/{repo}/issues on GitHub and POST /projects/{encoded-path}/issues on GitLab, with the title, body and labels. The response is normalized by the existing pure issue mappers, so the new card is identical to a refreshed one. Tokens stay in the 0600 store under the fluid home and never enter a response or an error.
  • Sub-tasks and milestones are rejected for remote creation; the normalized model has no portable wire mapping for them yet. Remote issues remain read-only for updates and status moves.
  • GitLab’s device scope becomes api (was read_api) because issue creation needs write access. Accounts connected with the old scope must reconnect once.
  • Local creation is unchanged: an in-memory Task with a local:N key and todo status. Durable .claude/issues/*.md write-back stays a separate follow-up.

Consequences

  • The Board notice names the target actually written (local:14 or github:owner/repo#77), so a fallback is visible instead of silent.
  • A forge refusal is surfaced as an error, with a fixed “check account permissions” message for 401/403; no local issue is created after a failed remote write.
  • Newly opened remote issues appear in Todo because both mappers treat open/opened as todo.
  • The issue-create permission is an additive capability in a server-only route; no agent-facing MCP create tool is introduced.
  • GitHub repo scope already covers issue creation; GitLab users reconnect to grant api.

Dogfood note

The write path was exercised with local HTTP doubles for both forges: the route resolves the active repository, posts the normalized payload with a bearer token, maps the returned issue into the board and reports the target. The fallback and missing-connection cases were covered with the demo state. A live device approval still needs the bundled OAuth clients.
