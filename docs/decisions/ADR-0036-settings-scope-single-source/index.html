ADR-0036 — One source of truth for project trust and project settings

  • Status: accepted
  • Date: 2026-11-26
  • Relates to: ADR-0007, ADR-0011, ADR-0021, ADR-0022, ADR-0034

Context

Settings had two competing vocabularies and two competing write paths:

  • GET /api/settings/project was read-only in the UI, while PATCH /api/projects/{id} already existed in Rust (ProjectPatch) and rewrites .fluid-coding/project.json. The web client exposed only list and activate, so project declarations could not be edited outside /setup.
  • apps/web/src/lib/agents.ts offered propose-first / checkpoint / read-only in the Agents page. Nothing consumed them. The dock’s AgentControls already used the implemented propose / edit / auto values from agentTrustModeSchema, and projectTrustSchema uses the same three values for the project default.
  • PATCH replaces the whole ProjectSettings object. projectSettingsSchema requires tags, but ProjectSettingsView did not expose them, so a client patch built from the view would silently erase the project’s tags.
  • ADR-0007 fixes the trust default at propose; ADR-0011 fixes the normalized task-provider domain; ADR-0022 fixes machine-level settings under the user’s fluid home, outside the checkout. None of those decisions is changed here; the settings UI was simply mixing their scopes.

Decision

  1. The project manifest .fluid-coding/project.json, owned by Rust, is the only persistent source for defaultTrust, plugins, tags and taskProviders. The web writes it exclusively through PATCH /api/projects/{id} with a body validated by projectPatchSchema; the route returns the rewritten Project and the UI reloads GET /api/settings/project after a successful save.
  2. ProjectSettingsView exposes tags from project.settings.tags (Rust struct and zod contract). A patch built from the view always carries those tags forward. A missing tags field defaults to [] for older servers.
  3. There is one trust vocabulary: projectTrustSchema = propose | edit | auto. The legacy TrustMode section in lib/agents.ts is removed. The dock’s AgentControls selector keeps the same three values but is a run-level override: it applies to the current agent turn only and is never written to the manifest. The Project settings panel edits the persistent project default. ADR-0007’s propose remains the default for new projects and for a run with no override.
  4. taskProviders in the manifest is a declaration selecting the normalized providers of ADR-0011 (local, github, gitlab); saving that list neither creates issues nor stores credentials. Forge tokens and machine-level LLM choices, theme, rail position and trace toggles remain in the fluid home as decided by ADR-0021 and ADR-0022, with debounced autosave. Project settings use an explicit Save button because a patch rewrites a file inside the repository.
  5. Wire shapes stay in Rust; zod validates both the server response and the outgoing patch at the boundary. No domain logic moves into React: pure draft/patch helpers live in settings/projectModel.ts, and the hook only loads, drafts, saves and reports saving / saved / error inline. In mock mode projectsApi.update rejects honestly instead of pretending to rewrite a manifest.

Consequences

  • Editing Project settings rewrites the manifest and is therefore explicit and visible; General settings keep their “applied as you change it” behaviour.
  • Tags can no longer be lost by a settings round trip; the shared fixture fixtures/contracts/settings-project.json is checked by both Rust and zod tests.
  • The Agents page and the dock speak the same trust language. A run-mode choice cannot be mistaken for a persisted project policy, and the dead propose-first / checkpoint / read-only labels disappear from the product.
  • A failed save surfaces inline (error), and a successful one reports saved without navigating away. A mock-mode session sees a clear “needs the server” error on Save.
  • ADR-0007, ADR-0011 and ADR-0022 are unchanged: this ADR only assigns each setting to its proper scope and closes the read-only gap in the Project panel.
  • ProjectPatch.settings remains a full replacement, not a merge. Any future field added to ProjectSettings must also be added to the view and to patchFromView, or it will be erased on save; the shared fixtures and contract tests are the guard.
