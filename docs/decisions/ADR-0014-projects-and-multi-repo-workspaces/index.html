ADR-0014 — Projects are multi-repo workspaces

  • Status: accepted
  • Date: 2026-11-25

Context

The first POC has one FLUID_WORKSPACE, one code graph and one matrix. Real work is different: a person moves between several projects, and one project is often several repositories (an app, a backend, a shared library, an infrastructure repo). A monorepo is only one special case. The backend cannot assume one checkout, and the frontend cannot show a single flat file tree as if it were the whole project.

This is a local-first workbench: no hosted registry is required to define or switch projects.

Decision

Separate three concepts:

  • Project: a persistent local definition with an id, a name, repository members and project-level settings (trust defaults, plugins, tags, task providers).
  • Workspace: the active local checkout of a project. It has a root path and a set of repository roots.
  • Repository: one checkout inside the workspace, with a stable repoKey, a local path relative to the workspace, an optional remote URL and a default branch.

A project definition lives in .fluid-coding/project.json inside the project root and is discoverable from a local ~/.fluid-coding/projects.json index. Neither requires a network service.

The server model becomes project- and repo-aware:

  • ProjectRegistry loads projects and activates one at a time. The first implementation keeps one active project per server process; API paths are additive so later instances can host several.
  • GET/POST /api/projects, GET/PATCH /api/projects/{id}, POST /api/projects/{id}/activate and GET /api/projects/{id}/repos expose the local model.
  • Existing graph, matrix, impact, task, edit and checkpoint routes accept an active project scope. Repo-scoped variants use /api/projects/{id}/repos/{repoKey}/.... Flat routes stay as the single-repo compatibility view.
  • Path validation is relative to the member repository, never only to the workspace root. A path must resolve inside the repo it claims; cross-repo writes are separate, explicit patches.
  • Entity keys are namespaced at project level as <repoKey>::<path>#<symbol>. Providers keep their local keys; the project layer adds the prefix when composing graphs.
  • FilePatch gains an additive repo field (default: the active repo) and checkpoints record the repo key. Restoring a checkpoint restores files in their original repository.
  • Cross-repo edges come from dependency manifests and language imports. They are typed relations with provenance, not guessed from paths.
  • Indexes, graphs and caches are keyed by (projectId, repoKey, commit) so work is reused per repo and composition stays fast. This preserves performance budgets.

The frontend becomes project-aware without becoming a monorepo-only UI:

  • A project switcher in the shell selects the active project; the URL carries project and optional repo so views are shareable.
  • The structure map shows one lane per repository, with cross-repo edges rendered as links between lanes. Miller columns are scoped to the selected repo by default and can widen to the project.
  • The editor tab label includes the repo. “Open in VS Code” uses the member repo’s absolute path.
  • The agent dock receives the active project/repo context in the task brief. A patch can touch multiple repos only when the agent returns explicit repo fields and trust allows it.
  • Plugins declare supported repoKey/language pairs. A native or WASM provider can be activated per repo; a web plugin renders in project-level slots without knowing where data came from.

Consequences

  • A single-repo project is the degenerate case and must keep working unchanged.
  • Adding multi-repo support is additive in the wire contracts: repo, projectId and namespaced keys.
  • Existing flat routes remain for the POC and delegate to the active project/repo.
  • Trust and checkpoints must be evaluated per repo; a bug in one repo cannot write into another.
  • Cross-repo intelligence depends on real dependency edges. Missing edges are reported as unknown, not invented.
  • Project switching is a local state change; no account, server or cloud sync is introduced.

Out of scope

  • Hosted project registries or multi-user projects.
  • Running one server process per repository.
  • Automatic detection of every possible package-manager relationship in the first slice; start with explicit project config plus TS/JS package imports.
