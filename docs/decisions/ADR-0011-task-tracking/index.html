ADR-0011 — One normalized Task domain for local and forge workflows

  • Status: accepted
  • Date: 2026-11-25
  • Deciders: Benoit, fluid-coding team

Context

The team workflow in badetitou-team tracks the same work in three places: local Markdown issues in .claude/issues/ managed by board.py (id, title, status, parent, branch, labels, created, updated), GitHub issues, sub-issues and Projects boards, and GitLab work items, child tasks, issue boards with workflow::* labels and milestones. Across all three the unit of work is one issue → one branch (<id>-<slug>) → one reviewable change with Refs #<id> and no attribution (PR/MR on a forge, in-review locally); the implementer receives a short brief instead of the whole session.

fluid-coding must show that work next to code: symbols, cells, Change Briefs and agent sessions. Reading three different issue shapes in the shell would duplicate status names, filters and task→code links in TypeScript.

Decision

  1. One Task domain in fluid-core. TaskSource is local | github | gitlab, TaskStatus is todo | in_progress | in_review | done, and keys are stable: local:12, github:owner/repo#12, gitlab:group/project#7. A task carries parent/children, labels, assignees, milestone, branch, remote reference and links to symbols, cells, changes and pull requests. TaskStore owns pure filters/sorts; core has no I/O.
  2. Local Markdown is the interoperable edge. Parse and serialize the board.py frontmatter shape (statuses todo, in-progress, in-review, done) and the Context / Acceptance criteria / Out of scope body. Unknown frontmatter keys are tolerated on input; output uses the board field set plus optional fluid links.
  3. Briefs are generated, not authored by a model. make_brief extracts the three body sections into a 10–20 line handoff with branch <number>-<slug> and footer Refs #<number>, plus files, commands and rules supplied as context.
  4. Capabilities describe providers, not connections. /api/tasks/providers returns manifests with read/create/update/moveStatus/subTasks/board/milestone/pullRequests flags. Only local tasks can be created, and writes mutate the in-memory store. GitHub and GitLab exist as keys, fixtures and advertised capabilities; live forge adapters are a later slice.
  5. Rust owns the wire. camelCase JSON from fluid-core is mirrored by zod schemas in packages/contracts/src/tasks.ts and checked by fixtures/contracts/tasks.json. The web Tasks board stays mock-first; VITE_API_MODE=server points it at Rust.

Consequences

Positive:

  • One board, one set of status filters and one task→code link vocabulary across providers.
  • Local issue files remain usable by board.py; existing issues need no migration.
  • Briefs are deterministic and testable; the implementer gets context without session history.
  • Providers can be advertised before credentials exist, and the shell can show what is not wired.

Negative:

  • Status naming has two encodings: snake_case on the wire, kebab-case in local frontmatter. Core maps both, and they must stay aligned with board.py and forge labels.
  • GitHub/GitLab entries are not live; capability flags must not be read as “sync implemented”.
  • Create/patch is not durable yet; file persistence and forge writes remain outstanding.
  • Task keys contain : and #, so clients must percent-encode path segments.

Alternatives considered

  • Forge as the only source of truth. Rejected: many projects have no remote, and the local flow has no PR; the board must work offline.
  • Tasks in a database. Rejected: the repository is the source of truth and local issues are plain committed files; a database adds a deployment and an export step.
  • Provider adapters in TypeScript. Rejected: duplicates filters and links in the presentation layer and breaks the Rust-first boundary; adapters belong behind core ports.
  • LLM-authored briefs. Rejected: extraction from structured issue bodies is deterministic, cheaper and reviewable; enrichment can be added later.

Migration

No production task data exists. Local issues keep their board.py shape and can be adopted by path. GitHub/GitLab tasks are normalized snapshots only until forge adapters are added.
