ADR-0038 — One chat field, two independent flows

  • Status: accepted
  • Date: 2026-11-26
  • Deciders: Benoit
  • Depends on: ADR-0035 (task intake chat)

Context

Home rendered TaskComposer, a bespoke intake bar: a short transcript, ⌘/Ctrl+Enter, and a plain textarea with a status line. The right dock rendered AgentDock with a terminal-style chat field: a › prompt line, two-row textarea, context/settings popovers and chips for trust mode, provider and model. The two fields looked different even though both talk to a Fluid Agent through General settings.

The user asked to share the field only, not the whole chat surface: Home keeps its intake purpose (next task → draft issue → Create), its short transcript and its page grid. It must not grow the dock’s Chat/Changes/History tabs, its New conversation button or its durable session list. The two flows must stay independent: sending in one does not select a conversation in the other.

Decision

  1. Extract the field from AgentRunForm. components/agent/ChatField.tsx renders the prompt line, textarea, context/settings popovers, agent chips and send button. AgentRunForm (dock) and TaskComposer (Home) both render it with their own labels, state and actions. ChatComposer stays the lower-level textarea/send primitive; AgentControls stays the chip row.

  2. Keep the two flows separate. The dock keeps its local useAgentWorkbench reducer and server sessions. Home keeps the pure taskComposer reducer through createComposerRunner and its draft card. No browser-local conversation store, no new selection events and no shared active id.

  3. Provider and model are genuinely shared. hooks/useChatSettings.ts reads and patches the same machine-level General settings as the dock and Settings → General, and listens to both settings events. A provider/model change in either chat field is reflected in the other without a reload.

  4. Home keeps its intake semantics. The endpoint fixes TrustMode::Propose and sends no files (crates/fluid-server/src/routes/task_intake.rs), so Home shows the mode and context chips in the same place but disabled, with titles explaining that they apply to coding runs in the dock. Its status chip says Creates in <project> · ⌘ Enter; the send button opens the draft card, never a patch. The gear popover has an intake note instead of the dock’s issue input.

  5. Home keeps ⌘/Ctrl+Enter. A plain Enter inserts a newline, as before; the dock keeps Enter-to-send and Shift+Enter for a newline. The shared field only shares appearance and the provider/model selection, not input handling.

  6. Both fields load on demand. Shell lazy-loads the agent workbench; NowPage lazy-loads TaskComposer (and with it ChatField and the settings schemas). The bundle gate stays under 150 KiB gzip.

Consequences

Positive:

  • The two input fields are visually identical, including the terminal prompt line and all chips.
  • The task-intake flow, the drafter and the server contract are unchanged; no new endpoint or store.
  • Provider/model choices stay consistent across Home, the dock and Settings → General.
  • Home has no chat-shell controls, so it remains a task-intake surface rather than a second agent dock.

Negative:

  • Mode and context chips are disabled on Home; selecting edit there would be a lie because the intake endpoint always proposes a draft and receives no files.
  • The two fields still have different send shortcuts and separate state. A change to ChatField affects both surfaces and needs both test paths.
  • Settings loads asynchronously in Home; the initial render shows “loading…” in the provider chip.

Alternatives considered

  • Render AgentDock on Home. Rejected: it would add tabs/history and run patches from Home, and the two surfaces would share one dock id and sheet state.
  • Move the whole chat shell to a shared ChatPanel. Rejected by the user: only the field was in scope; tabs, history and new-conversation controls must stay in the dock.
  • Extend the intake contract with trust and files. Rejected: it would change Rust, zod and the server route for a field that is meant to draft an issue, not apply code.
  • Lift one shared workbench to a React provider. Rejected: the user asked for independent flows, and the two reducers model different things (runs/patches versus drafts/issues).
