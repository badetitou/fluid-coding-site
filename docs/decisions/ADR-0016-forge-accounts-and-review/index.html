ADR-0016 — Connected forge accounts and read-only review access

  • Status: accepted
  • Date: 2026-11-25

Context

fluid-coding needs to review existing GitHub PRs and GitLab MRs (cloud and self-hosted) from a user’s connected accounts. The first release only reads: list accounts, add/remove an account, list reviews, fetch one review. Posting comments, approving or merging is deliberately out of scope.

The fluid-core crate must stay pure and wasm32-compatible: no reqwest, no filesystem, no environment access. HTTP adapters, credential storage and UI belong to upper layers. We want one typed seam, as with AgentPort, so adapters and the web layer cannot invent their own shapes.

Decision

Add ForgePort in fluid-core with a manifest() and an object-safe boxed-future fetch():

pub trait ForgePort: Send + Sync {
    fn manifest(&self) -> PluginManifest;
    fn fetch<'a>(
        &'a self,
        request: &'a ForgeRequest,
    ) -> Pin<Box<dyn Future<Output = Result<ForgeResponse, PluginError>> + Send + 'a>>;
}

There is no async-trait dependency. Failures are PluginError; the core never performs I/O.

PluginKind::Forge, PluginPermission::ForgeRead and PluginPermission::ForgeWrite are additive. The contract version stays at 1. forge_manifest(kind) declares id forge:github / forge:gitlab, label GitHub / GitLab, version 0.1.0, PluginKind::Forge, PluginRuntime::Native, PluginHost::Server, capabilities ["reviews:read"] and permissions ["network:out", "forge:read"]. forge_write_manifest(kind) is a declared-only variant (forge:github:write / forge:gitlab:write) with forge:write; no adapter implements it yet.

Account model and authentication

ForgeAccount { id, kind, label, baseUrl?, username, authMethod, scopes } is a public, loggable value. It MUST NOT contain a token. Secrets live in the server-side secret store; neither this type nor any ForgeResponse ever carries them. ForgeAccountInput is the only token-bearing type: it exists on add-account requests, implements Debug manually as token: "***", and never derives Serialize as a type-level guarantee — its hand-written Serialize is what emits the request wire shape. validate_account_input rejects blank labels/usernames, PATs shorter than 8 characters and invalid base URLs; errors never echo the token.

Auth is PAT-first: ForgeAuthMethod::Pat ("pat") is the only implemented method. ForgeAuthMethod::OAuthDevice ("oauth_device") is declared for the future device-flow work; adapters must reject it until that flow exists. baseUrl is optional: plain github.com and gitlab.com use the adapter default. Self-hosted GitLab sets https://gitlab.example.com. Only https is accepted, except http://localhost / http://127.0.0.1 for local test setups. A GitHub baseUrl must name a GitHub Enterprise host — https://github.com (and its subdomains) is rejected instead of silently overriding the default.

Token storage: the server keeps tokens in its secret store, never in the repo, project manifest, logs, Change Briefs or the browser. For this prerelease that store is a file outside the repository with mode 0600; an OS-keychain backend is the follow-up. Removing an account deletes the stored secret as well as the public account record.

Wire contract

ForgeRequest and ForgeResponse use an internally tagged kind field, camelCase names and snake_case enum values. Both Rust enums keep their newtype variants; a private wire enum carries the serde tag (serde cannot internally tag a newtype holding a Vec, and AddAccount would collide with the input’s own kind field if it were flattened). The exact JSON is:

// requests
{ "kind": "listAccounts" }
{ "kind": "addAccount", "input": { "kind": "gitlab", "label": "GitLab",
  "baseUrl": "https://gitlab.example.com", "username": "alice",
  "token": "glpat-…", "scopes": ["api"] } }
{ "kind": "removeAccount", "id": "acct-gl" }
{ "kind": "listReviews", "accountId": "acct-gh", "state": "open" }  // state optional
{ "kind": "getReview", "accountId": "acct-gh", "id": "github:badetitou/fluid#8" }

// responses
{ "kind": "accounts", "accounts": [ForgeAccount] }
{ "kind": "account", "account": ForgeAccount }
{ "kind": "removed", "id": "acct-gl" }
{ "kind": "reviews", "reviews": [ForgeReviewSummary] }
{ "kind": "review", "review": ForgeReviewDetail }

ForgeAccount.baseUrl, ForgeFileChange.patch and ForgeCheck.url are omitted when absent. Enum values: kinds github / gitlab; auth pat / oauth_device; review states open / merged / closed; file statuses added / modified / removed / renamed; check statuses passed / failed / pending / unknown. Review ids are canonical and globally unique: github:owner/repo#8, gitlab:group/proj!12 (review_id(kind, project, number)).

packages/contracts/src/forge.ts mirrors every wire type with zod. Account response schemas additionally reject any object containing a token field, even though zod would otherwise strip unknown keys: defence in depth against an adapter accidentally returning a secret. The shared fixture lives in fixtures/contracts/forge.json.

Why Change Briefs, not a second review model

to_change_brief(&ForgeReviewDetail) -> serde_json::Value maps a review onto the existing ChangeBrief vocabulary in crate::change: version, id, base, head, createdAt, files (path, status, additions, deletions, binary), empty symbols / cells / tags, checks (id, label, status, evidence) and a transparent risk. Forge removed becomes brief deleted; check statuses become pass / fail / warn / skip; a check URL becomes evidence. Paths stay symbol-less because forge APIs do not provide the graph’s symbol keys, and no fabricated symbols are allowed. The review body, commit messages and author opinions are not evidence and are not mapped. Commits remain available on ForgeReviewDetail for a future UI, but the shared reasoning model stays one vocabulary: one brief per review, consumed by the same impact/risk/ narrative pipeline as local changes. A separate review model would fork that pipeline and create a second notion of “what changed”.

Consequences

  • Backend and frontend adapters can be built against stable, typed contracts without touching the core.
  • Review reads work offline-testably with fake ForgePort implementations; no network in core tests.
  • Only forge:read is implemented. Comments and approvals need the separate forge:write capability, an explicit user opt-in and their own tests.
  • Adding a forge (or a device-flow auth method) is a new adapter plus manifest, not a route or UI special case.
  • The zod pluginKindSchema / pluginPermissionSchema lists in agents.ts must include forge, forge:read and forge:write for generic manifest validation; forge.ts provides forgeManifestSchema in the meantime.
