ADR-0012 — First POC includes editing, adapters, Monaco/LSP, more languages and LLM narrative

  • Status: accepted
  • Date: 2026-11-25
  • Deciders: Benoit
  • Supersedes: the “understand + review first” sequencing in earlier planning notes

Context

The first plan made chat-driven editing, non-MCP agent adapters, Monaco/LSP, Java/Pharo providers and LLM narrative later phases. That would produce a read-only viewer, not something the maintainer can dogfood: the point of the second shell is to run a task, hand it to a real agent, review the patch, check it and continue in the same place. The local installable app makes this loop testable every day.

Decision

The first POC must demonstrate the whole loop, with narrow but real slices:

  1. Chat-driven code editing. A chat turn can produce a patch proposal; the user reviews hunks, applies them, and can restore a checkpoint. Default trust mode is propose; edit/auto stay explicit and checkpoint every write (ADR-0007).
  2. Agent adapters behind AgentPort. MCP stays the read-tool substrate. opencode and Claude Code adapters are first-class implementations behind the same port, with a fake adapter for tests.
  3. Monaco/LSP editing. The code surface is a real editor with LSP-style navigation; “Open in VS Code” remains the escape hatch. Monaco is loaded lazily so the initial shell stays FAF.
  4. Language providers. TypeScript/JavaScript are the first-class static providers; Java and Pharo (Tonel static first, live via MCP where available) ship in the POC with the same provider contract.
  5. LLM narrative as enrichment. Every brief/Change Brief is complete and deterministic without a model. An optional LLM turn adds a short narrative, clearly separated from facts and never used as evidence.

The installable local app (Rust binary + macOS .app, embedded web, fluid-derived logo) is the delivery vehicle for this POC.

Consequences

  • The POC is larger than a viewer; work is split into independently reviewable vertical slices so no single change blocks dogfooding.
  • AgentPort, patch/checkpoint types and the provider contract become POC contracts, not future placeholders.
  • Every write path needs checkpoints and audit entries from day one; there is no “temporary” unguarded edit path.
  • LLM output is optional, attributable and never a source of truth for graph, impact or checks.

Alternatives considered

  • Keep the POC read-only. Rejected: cannot dogfood the editing loop.
  • Build each capability in isolation and integrate later. Rejected: integration risk lands at the end; slices must be end-to-end.
  • Make the LLM the editor. Rejected: patches come through reviewable tool/port boundaries; the model can propose, not silently write.
