ADR-0049 — Changes view: tree mode alongside the flat list

  • Status: accepted, implemented on branch 102-changes-view-tree-mode-alongside-the-fla; not yet merged
  • Date: 2026-11-27
  • Deciders: Benoit (to validate)
  • Amends: ADR-0022 (general settings home), ADR-0036 (settings scope)

Context

The Changes page showed one flat list of changed paths. Worktrees nest files several directories deep, so repo/apps/web/src/a/b/file.ts took a whole row and hid which directories actually changed. Grouping had to be a view choice, not a repository change: the same project can be reviewed as a flat patch list or as a tree, and the choice must survive reload/restart for the user, not for one checkout.

Decision

  1. Shaping is pure fluid-core. shape_change_tree(&[FileDiff]) -> Vec<ChangeTreeNode> builds one node per changed path segment, drops every folder with no changed file below it, recursively collapses single-child folder chains into one labelled row (repo/src/a/b/), aggregates additions/deletions/file counts, and orders folders before files. It has no I/O and compiles to wasm32. React never reshapes the tree; it only flattens the returned nodes into visible rows.
  2. One batched answer. GET /api/changes now returns { files, tree } with the flat diffs and the same diffs shaped once in Rust. No second git diff and no extra request when switching mode. ChangeTreeNode, changesResponseSchema and the shared fixtures fixtures/contracts/change-tree.json and fixtures/contracts/changes-response.json are validated on both sides. This is an intentional contract break: a stale client that still expects an array fails validation rather than silently showing a partial tree. The macOS app embeds matching web assets, so mixed versions are not a supported pairing.
  3. The mode is machine-level General settings. changesViewMode: 'list' | 'tree' defaults to list, lives in ~/.fluid-coding/general-settings.json and is read/ patched through /api/settings/general; it is never stored in .fluid/, browser storage or the URL. The Settings → General segmented control and the Changes page toggle write the same setting and stay in sync through the existing settings events. The hook is imported only by the lazy Changes page, so the settings seam adds nothing to the initial JS chunk.
  4. Both modes share the row affordances. Full paths are in title tooltips, labels ellipsize, the empty state renders in either mode, and folders expand/collapse locally without changing the shaped data.

Consequences

  • The contract break is deliberate and small: one endpoint changes from an array to an object; the zod schema and the web loader move together, the server route test proves both lists start empty, and a shared response fixture is parsed by Rust and zod.
  • Legacy settings files without changesViewMode parse to list; unknown values are rejected by both Rust and zod.
  • A path that is both a file and a directory (file→directory transition) keeps both rows, and duplicate paths aggregate into one row: no changed file disappears from the tree.
  • General settings writes are serialized server-side (settings_write mutex), so a Changes toggle cannot lose a concurrent provider/model patch from the dock or another field.
  • The tree is derived per changes response, not cached in the repository or in React state; a new review target naturally produces a new tree on the next load.
  • Bundle check stays under the 150 KiB gzip initial-JS budget (142.0 KiB measured on this branch).
