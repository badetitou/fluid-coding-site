ADR-0029 — Start Work runs the Fluid Agent in a task worktree

  • Status: accepted
  • Date: 2026-11-26
  • Deciders: Benoit

Context

The Tasks board’s Start work button only created or switched to the task’s branch. That guarded the one-issue-one-branch flow from ADR-0011, but it also refused to run whenever the main checkout had uncommitted changes — the normal state while dogfooding the app. The user wants the button to hand the selected task’s brief to the configured agent, not to return the working tree has uncommitted changes; commit or stash them before starting a task.

Agents already run behind one AgentPort (ADR-0024), and the CLI adapter accepts a working directory. Patch apply/checkpoint restore, however, resolve paths against the active project’s workspace root.

Decision

  1. POST /api/tasks/{key}/start creates or reuses an isolated git worktree for the task’s branch at .fluid-coding/worktrees/<sanitized-key>-<fingerprint>/ inside the active repo. It never checks out a branch in the main workspace and never stashes user work. The index layer owns the git write; the core stays pure.
  2. The server builds a deterministic handoff prompt from make_brief (handoff_prompt in fluid-core) and passes it with the brief to the fluid agent, which follows the provider selected in Settings → General. The agent process runs with the worktree as its cwd.
  3. The run is recorded like any other agent turn: durable chat session plus session analysis entry. Proposed patches are registered with the edit plugin and carry a worktree root, so apply and checkpoint restore target that worktree. The Tasks board announces the run and opens the agent dock on its conversation.
  4. Local tasks move to in_progress and record their branch after a successful start. Remote issues stay read-only; their normalized snapshot is unchanged.

Consequences

Positive:

  • Uncommitted work in the main checkout no longer blocks a task, and the agent sees a clean tree.
  • Reusing the same worktree for a task keeps repeated starts idempotent and preserves agent-written files between runs.
  • One AgentPort and one brief generator serve both the dock and task starts; no second tool loop.
  • Patch review stays reversible: checkpoints capture the worktree’s prior contents.

Negative:

  • Worktrees consume extra disk and leave git metadata under the main repo’s .git/worktrees; they are not removed automatically when a task is done.
  • A branch already checked out in another worktree makes the start fail with a typed git error.
  • The agent’s cwd is the task worktree, while the Code/Monaco page still shows the main checkout; users must open the worktree path to see files the agent wrote directly.
  • Existing unregistered patch proposals from older runs still apply to the main workspace.

Alternatives considered

  • Auto-stash then switch branch. Rejected: restoring a stash over files an agent may have changed is easy to get wrong, and silent stashing hides user work.
  • Run in the main checkout without a branch. Rejected: the agent would mix its changes with unrelated uncommitted work and break ADR-0011’s review unit.
  • Keep the current branch-only button and add a separate agent button. Rejected: the board would expose two overlapping handoffs and the same dirty-tree failure would remain.
