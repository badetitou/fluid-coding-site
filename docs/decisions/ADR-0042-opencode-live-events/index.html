ADR-0042 — opencode runs report live tool calls through opencode serve

  • Status: accepted, implemented on branch opencode-live-events; not yet merged
  • Date: 2026-11-27
  • Deciders: Benoit (to validate)
  • Amends: the opencode branch of the CLI adapter (crates/fluid-server/src/agents/cli/); extends ADR-0041 for opencode only. AgentPort and AgentEvent are unchanged.

Context

ADR-0041 streams opencode through opencode run --format json. Probing that output (2026-11-27) shows it reports a tool call only when the call has finished:

  • A sleep 25 shell call produced no event for 25 seconds, then one tool_use with state.status: "completed".
  • opencode session export during the run does not show the running call either; the assistant message is written when its step completes.
  • A sub-agent (subagent/task) runs in its own session. Its activity is read back only after the whole run ends.

So a running tool is invisible in the dock, which shows only “Working…”. This is the symptom the user reported.

opencode serve (v2.4.2) exposes the events the CLI does not print. Probed locally:

  • GET /api/event is a server-sent event stream. It sends server.connected, session.created, and a : heartbeat comment.
  • The event enum includes session.tool.called, session.tool.progress, session.tool.success, session.tool.failed, session.text.delta / session.text.ended, session.step.*, session.idle, session.status, permission.asked and permission.replied.
  • Sessions are created with POST /api/session; messages are sent with POST /api/session/{id}/prompt (text, files, metadata, resume); runs are stopped with POST /api/session/{id}/interrupt; permissions are answered with POST /api/session/{id}/permission/{requestID}/reply.
  • The server prints a generated password at start-up and requires HTTP basic auth. The password must never be logged or stored in the repository.

Decision

  1. Transport. The opencode adapter starts opencode serve --hostname 127.0.0.1 --port <free> for the run, reads the password from the server’s start-up output, and talks to it over loopback only. A run creates a session (or resumes the conversation’s recorded session), sends the prompt, and consumes GET /api/event filtered to that session until session.idle.
  2. Mapping. Events map onto the existing AgentEvent values:
    • session.text.delta → Text;
    • session.tool.called → ToolStarted (shown while running);
    • session.tool.progress → updates the running tool’s preview;
    • session.tool.success / session.tool.failed → ToolFinished;
    • events from a child session → Nested under the call that started it, using the child session id from the subagent call’s metadata as soon as it is known, not at the end. The mapping lives in its own module, separate from the CLI line parser.
  3. Permissions. --auto (trust auto, worktree only) answers permission.asked with a one-time approval. Every other trust mode denies or leaves the request pending and the run says so. No permission is approved silently in the dock or intake (both stay read-only).
  4. Model and agent. The model and agent come from the same settings as today, passed in the prompt or session call, not through argv.
  5. Stop. Stop calls interrupt and then ends the server’s process group, reusing the existing RunHandle stop path.
  6. Fallback. If opencode serve cannot start or authenticate, the run fails with a typed error that names the step. It does not silently fall back to run --format json, because that path hides tools. A setting may keep the old path for users who need it; this is not default.
  7. Size. The adapter is a new module directory (agents/opencode_live/: process lifecycle, HTTP and SSE client, event mapping). Each file stays under 300 lines.

Consequences

  • Running tools and sub-agent calls appear while they run. The 600 ms polling of the pending conversation is unchanged; the transport between server and browser is still polling (ADR-0041).
  • A new runtime dependency is needed for HTTP and SSE in fluid-server (check the current Cargo.toml for an existing HTTP client before adding one).
  • Each opencode run starts a local server process. Its cost and start-up time must be measured; reusing one server for consecutive runs is a possible later step, not part of this ADR.
  • opencode’s HTTP API is marked experimental in parts. Event names and payloads are external and must be pinned by recorded fixtures, as the CLI formats are today.
  • Claude and the other CLIs are unchanged.

Verification plan

  • Unit tests: map recorded event fixtures (text, tool called/progress/success/failed, child session) to AgentEvents, including a tool that is still running.
  • Fake server test: an SSE fixture replayed over loopback, checking stop, auth failure and a permission request in each trust mode.
  • Dogfood: run a task with a 25-second shell call in the dock and confirm the call shows as running before it finishes; run a sub-agent and confirm its calls appear while it runs.
  • Gates from CLAUDE.md: cargo test --workspace, cargo clippy --workspace --all-targets -- -D warnings, cargo fmt --all -- --check, pnpm test, pnpm -r typecheck.

Open questions

  • One server per run, or the shared opencode service (--server attaches to a running server)?
  • Should the setting that keeps the old run --format json path exist at all?

Implementation notes

What the code does, where it differs from the plan above:

  • Scope: a command whose program is named opencode runs through the server. Any other program keeps the plain command path (streams_through_server in agents/cli/mod.rs).
  • Code: agents/cli/opencode_live/ with serve.rs (process and startup lines), client.rs (HTTP and event stream), events.rs (pure mapper, tested on recorded fixtures) and mod.rs (the run). Fixtures are in crates/fluid-server/fixtures/opencode-live/, recorded from opencode 2.4.2.
  • Running tools: a call is shown when opencode emits session.tool.called, with its input.
  • Sub-agents: a sub-agent’s session is read from the call’s session.tool.progress metadata, while it runs. Its events are nested under the call. Events that arrive before that link are held.
  • Finish: the run ends when no session is executing and no inbox item is queued, after a 1.5 s grace period. A finished sub-agent queues its result for its parent, which then runs again.
  • Stop: the server’s process group is killed, as for the CLI path. The interrupt call is not used.
  • Permissions: auto trust approves every request. edit trust approves edit and write requests. Other requests are rejected.
  • Model and agent: -m provider/model#variant and --agent from the command become the session’s model and agent. Each run starts a new session, as the CLI path did; runs do not resume sessions.
  • Verification: unit tests on the mapper, a fake server for the whole run, and an ignored test that runs the real CLI (cargo test -p fluid-server real_opencode -- --ignored).
